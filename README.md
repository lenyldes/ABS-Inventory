# ABS Inventory & Procurement Assistant

Бэкенд-сервис для складского учёта, предиктивного анализа потребности и планирования закупок. \
Написан для SPA-оператора на стеке **Python 3.11, FastAPI, PostgreSQL 18 и Docker Compose**.

> 🚀 **AI-Assisted Engineering — инженерный бенчмарк совместной разработки с ИИ:** \
> Проект спроектирован, реализован и развёрнут на сервере за **2 дня** плотной работы с ИИ-ассистентом: \
> — **110+ атомарных коммитов**, каждый шаг проходил ручной аудит (*Stop-and-Review*); \
> — **12 OpenSpec-спецификаций** (65+ формализованных требований, закрывающих всё ТЗ и бизнес-контекст СПА); \
> — **~30 000 строк Python-кода** в 200 модулях модульного монолита (0 замечаний Ruff, жёсткий лимит `<= 10 000` символов на файл); \
> — **355+ тестов** в pytest, приёмка Zero-Defect в изолированных контейнерах; \
> — **Боевой стенд с авто-TLS**: [abs-inventory.lenyldes.ru](https://abs-inventory.lenyldes.ru) — интерактивное тестирование API в браузере в один клик.

## 1. Демонстрационный стенд (Live Demo)

- **Публичный адрес**: **[https://abs-inventory.lenyldes.ru](https://abs-inventory.lenyldes.ru)**
- **Интерактивная документация OpenAPI (Swagger UI)**: **[https://abs-inventory.lenyldes.ru/docs](https://abs-inventory.lenyldes.ru/docs)**
- **Сервер**: Raspberry Pi 5 (Debian 13, ARM64), Docker Compose, обратный прокси Caddy 2 с автоматическим TLS Let's Encrypt и HTTP/2.

### Возможности веб-интерфейса
- **Проверка API (интерактивный стенд)**: не нужно настраивать Postman или копировать curl-команды — на первом экране есть готовые карточки всех ключевых методов из ТЗ (движения, остатки, ошибки FEFO, прогноз, риски, план). Тело запроса и результат в БД видны до и после клика.
- **Сквозной маршрут**: пошаговое прохождение продуктовой цепочки *«Склад → Партии → Журнал → Риски → Прогноз потребности → План закупок → Бюджет»*.

## 2. Соответствие техническому заданию

| Требование ТЗ | Реализация в проекте | Эндпоинт / Модуль |
|---|---|---|
| **Регистрация движения** | Приход, расход, списание, возврат, корректировка; проверка дублей номеров (409) и дат из будущего (422) | `POST /api/movements` |
| **Журнал движений** | Фильтры по SKU, объекту, типу, периоду; пагинация (`limit`, `offset`, `total`) | `GET /api/movements` |
| **Остатки склада** | Расчёт из движений и партий, средний расход за 90 дней, запас в днях, ближайший срок | `GET /api/stock` |
| **Партии позиции** | Детализация по объектам, партиям, срокам годности, ценам прихода и накладным | `GET /api/stock/{sku}` |
| **Прогноз потребности** | Расход, остаток, поставки в пути, страховой запас, точка заказа, дата заказа, кратность упаковкам и мин. партии, блок `explanation` | `POST /api/forecast` |
| **Предупреждения по рискам** | Дефицит (запас < срок поставки), приближение просрочки, отсутствие движения; уровни важности | `GET /api/alerts` |
| **Списание по FEFO** | Списание с партии с ближайшим сроком; запрет расхода просроченных партий (только `writeoff`) | `app/inventory/fefo.py` |
| **Чистые расчёты** | Вся математика детерминирована, вынесена в чистые функции и тестируется без HTTP и БД | `app/forecasting/`, `app/procurement/` |
| **План закупок и бюджет** | Сводный бюджет на 1, 3, 6, 12 месяцев в разрезе месяцев, SKU, категорий и объектов | `POST /api/procurement/plan` |

## 3. Архитектура решения

Сервис построен как **модульный монолит** с чётким разделением ответственности:

```text
┌────────────────────────────────────────────────────────┐
│                   ТРАНСПОРТНЫЙ СЛОЙ                    │
│      FastAPI эндпоинты, DTO-валидация Pydantic v2      │
│         Статусы: 200, 201, 400, 404, 409, 422          │
└───────────────────────────┬────────────────────────────┘
                            │
            ┌───────────────┴───────────────┐
            ▼                               ▼
┌───────────────────────┐       ┌───────────────────────┐
│ СЛОЙ ДОСТУПА К ДАННЫМ │       │  СЛОЙ ЧИСТЫХ РАСЧЁТОВ │
│ SQLAlchemy 2.0 Repos  │       │ Чистые функции (Pure) │
│ - app/inventory/repo  │──────▶│ - app/inventory/calc  │
│ - app/forecasting/repo│       │ - app/forecasting/calc│
│ - stock_locks (Mutex) │       │ - app/procurement/plan│
└───────────────────────┘       └───────────────────────┘
```

### Как считается остаток (требование ТЗ)
Остаток **не хранится отдельным изменяемым полем** в БД — это исключает рассинхронизацию. Он рассчитывается на лету функцией `calculate_stock_balance` (`app/inventory/calculator.py`) на любую дату `as_of`:
$$\text{Stock}(sku, loc) = \sum \text{receipt} + \sum \text{return} \pm \sum \text{correction} - \sum \text{consume} - \sum \text{writeoff}$$
- **Доступный остаток**: только непросроченные партии ($\text{expiry\_date} \ge as\_of$ или без срока годности).
- **Просроченный остаток**: партии с $\text{expiry\_date} < as\_of$ уходят в `expired_quantity`, блокируются для отпуска (`consume`) и подлежат списанию (`writeoff`).
- **Конкурентные списания**: защищены транзакционными блокировками `stock_locks` (`SELECT ... FOR UPDATE` по товару и объекту).

## 4. Стек технологий и обоснование

- **Python 3.11 & FastAPI**: быстрая асинхронная обработка, строгая типизация, валидация контрактов через Pydantic v2 и автогенерация схемы OpenAPI 3.1.
- **PostgreSQL 18 & psycopg3**: промышленная СУБД с надёжной сериализацией транзакций, строгой проверкой внешних ключей и эффективной работой с блокировками.
- **SQLAlchemy 2.0 & Alembic**: современный декларативный ORM с явным разделением сессий и версионируемые миграции схемы БД.
- **Docker Compose**: полная изоляция и воспроизводимость запуска бэкенда, БД, веб-интерфейса и тестового контура одной командой.
- **Nginx & Caddy 2**: Nginx отдаёт веб-интерфейс и проксирует API внутри Compose; Caddy на хосте обеспечивает автоматический TLS Let's Encrypt и маршрутизацию по HTTP/2.
- **Pytest**: 355+ тестов (юнит-тесты чистых функций, транзакционные тесты БД, e2e-сценарии жизненного цикла Compose).

## 5. Быстрый старт (локальный запуск)

### Запуск проекта в Docker Compose
```bash
cp .env.example .env
docker compose up --build -d
```
При старте автоматически применяются миграции Alembic, инициализируются справочники и загружается демо-набор данных.

**Точки входа:**
- Веб-интерфейс: [http://localhost:8080](http://localhost:8080)
- Swagger UI (OpenAPI): [http://localhost:8000/docs](http://localhost:8000/docs)
- Health-check: `curl http://localhost:8000/health`

### Примеры API-запросов (curl)
```bash
# Проверка остатков на контрольную дату
curl -s "http://localhost:8000/api/stock?as_of=2026-09-29" | jq .

# Регистрация расхода по FEFO
curl -X POST "http://localhost:8000/api/movements" \
  -H "Content-Type: application/json" \
  -d '{"operation_date":"2026-09-29","sku":"DEMO-OIL","location":"DEMO-MS-01","type":"consume","quantity":5.0,"doc_number":"CONSUME-001"}' | jq .
```
*Подробная коллекция curl-запросов для всех методов ТЗ — в [doc/api_examples.md](doc/api_examples.md).*

## 7. Тестирование и Zero-Defect

Проект следует принципу **Zero-Defect**: перед каждым коммитом запускается единый проверочный контур.

```bash
# Запуск тестов в Docker:
docker compose run --rm -T test pytest -q

# Полный контур проверок (Ruff + лимит символов + pytest + E2E Compose):
bash scripts/check.sh
```

- **Статический анализ**: `ruff check .` и `ruff format .` (0 замечаний).
- **Лимит символов**: `python3 scripts/check_limits.py` (контроль `<= 10 000` символов на файл).
- **Сквозные E2E-тесты**: проверка сценариев запуска, сбоев Compose, двухфазных исправлений и веб-интерфейса.
