# Правила совместной работы и стандарты разработки (AGENTS.md)

Документ определяет обязательные правила, стандарты качества и порядок взаимодействия для ИИ-агентов и разработчиков в проекте **ABS Inventory & Procurement Assistant**.

---

## 1. Общие принципы и язык

1. **Русский язык**: Всё общение в чате, рассуждения, проектная документация, комментарии и описания коммитов ведутся на русском языке.
2. **Итеративность**: Работа ведётся небольшими проверяемыми шагами. Запрещено накапливать крупные нетестированные изменения.
3. **Архитектурное согласование**: Любые архитектурные предложения, спорные моменты и интерпретации требований сначала обсуждаются с пользователем и только после подтверждения реализуются в коде.
4. **Принцип экономии токенов**: Избегать избыточной бюрократии, длинных монологов и генерации промежуточных служебных файлов, если решение уже согласовано в диалоге.

---

## 2. Ограничение объёма файлов (<= 10 000 символов)

1. **Область проверки**: Проверке на объём подлежат создаваемые и поддерживаемые в проекте исходники и документация с расширениями `*.py` и `*.md`, включая новые файлы до коммита. Сторонние зависимости, виртуальные окружения, кэши, результаты сборки и служебные файлы инструментов агента не проверяются. Авторство по Git не используется: ранее написанные файлы проекта также остаются под контролем.
2. **Лимит символов**: Ни один целевой файл не должен превышать **10 000 символов** (включая пробелы и переносы строк в UTF-8).
   - Лимит защищает контекстное окно модели от перегрузки и предотвращает появление монолитных файлов.
   - 10 000 символов эквивалентны ~300–400 строкам кода при стандартной плотности.
3. **Декомпозиция вместо «утрамбовывания» (искусственного сжатия и минификации)**:
   - Превышение лимита **не означает, что код нужно «утрамбовывать» или сжимать**: категорически запрещено ухудшать читаемость, удалять комментарии, документацию, докстринги, аннотации типов, сокращать имена переменных или выбрасывать логику, проверки и функциональность ради укладывания в лимит.
   - Единственно правильный подход — **провести рефакторинг и декомпозицию**: логически вынести часть кода в отдельный файл (новый модуль, сервис, репозиторий, схему, хелпер), сохранив суть, полноту и корректность решения без потери функционала.
   - **Запрет промежуточных пересчётов**: агенту запрещено тратить токены на постоянные замеры и «упреждающие» подсчёты символов в процессе написания кода. Проверка лимита выполняется строго один раз в конце работы в составе тихих проверок Zero-Defect. При выявлении превышения файл декомпозируется, а не подгоняется под размер.
4. **Исключения**: Сводная генеральная дорожная карта `doc/ROADMAP.md` и исходные файлы требований заказчика в `doc/SOW/` являются допустимыми исключениями из лимита.
5. **Автопроверка**: Контроль выполняется тихим скриптом `python3 scripts/check_limits.py` однократно в конце работы перед остановкой на ревью в блоке Zero-Defect. Промежуточные запуски скрипта и ручные замеры символов после каждой отдельной правки запрещены.

## 3. Git-процесс и протокол остановки на ревью (Stop-and-Review)

### 3.1. Ветвление
- Каждое изменение OpenSpec изолируется в отдельной ветке:
  ```bash
  git checkout -b change/<name>
  ```
- Ветка `main` содержит только проверенный и завершённый код.

### 3.2. Формат коммитов
Сообщения коммитов формируются строго по схеме:
```text
<TYPE>: <краткое описание изменений на русском языке>
```

**Разрешённые типы (на английском языке)**:
- `ADD:` — добавление новой функциональности, модулей, тестов или документации.
- `UPD:` — обновление существующей логики, настроек, рефакторинг без смены назначения.
- `FIX:` — исправление ошибок, багов, опечаток.
- `RM:` — удаление неиспользуемого кода, файлов или зависимостей.
- `DOC:` — обновление или добавление документации без изменения кода.
- `TEST:` — добавление или модификация тестов.
- `REFACTOR:` — изменение структуры кода без изменения его поведения.
- `MERGE:` — слияние завершённого изменения в основную ветку.

*Правило анти-тавтологии*: Не дублировать глагол типа в описании (не `ADD: Добавить модуль`, а `ADD: модуль конфигурации приложения`).

### 3.3. Обязательная остановка перед коммитом (Stop-and-Review)
Агенту **категорически запрещено** выполнять `git commit` автоматически.

Перед каждым коммитом агент обязан:
1. Выполнить проверку Zero-Defect в тихом режиме (без вывода в чат при успехе).
2. Сформулировать и вывести пользователю **краткую сводку ревью** (без списков файлов, дублирования задач и логов):
   - **Суть изменений**: буквально 1–3 предложения простыми словами о том, что было сделано.
   - **Предлагаемый текст коммита**: строго по формату раздела 3.2.
   - **Ручные проверки**: указывать только при реальной необходимости (шаги ручной проверки, оценка UI, спорные вопросы). Если ручная проверка не требуется, пункт опускается.
3. **Остановиться** и дождаться явного подтверждения пользователя («коммить», «ок» или замечания).

### 3.4. Слияние и завершение изменения
После выполнения и фиксации всех задач изменения:
1. По запросу пользователя `/openspec archive` выполняется архивация OpenSpec в ветке изменения, включая синхронизацию спецификаций, если она требуется.
2. В этой же ветке обновляется статус в `doc/ROADMAP.md`. Этап отмечается `- [X]` только при выполнении его критерия завершения; отдельное изменение может закрывать лишь часть этапа.
3. Проводятся итоговые проверки и ревью архива и документации. Коммит выполняется после подтверждения по разделу 3.3.
4. После подтверждения слияния пользователем выполняются команды ниже. Подтверждение финального коммита и слияния можно получить одним явным ответом на сводку ревью. Рабочее дерево перед слиянием должно быть чистым.
   ```bash
   git checkout main
   git merge --no-ff change/<name> -m "MERGE: <краткое описание изменения>"
   git branch -d change/<name>
   ```

## 4. Взаимодействие с OpenSpec и ROADMAP

1. **Глобальный план**: Этапы проекта и их статусы отслеживаются в `doc/ROADMAP.md`.
2. **Порядок работы**: `/openspec-explore` — обсуждение задачи и решений; затем `propose` — подготовка предложения, спецификаций и задач в отдельной ветке. После ревью и подтверждения пользователя артефакты фиксируются отдельным коммитом.
3. **Реализация**: Для небольшой задачи `apply` выполняется целиком с последующим ревью и коммитом. Для большой — по согласованным шагам с проверкой, обновлением задач и отдельным подтверждённым коммитом после каждого шага. Подтверждение одного коммита не разрешает последующие автоматически.
4. **Завершение**: Когда все задачи закрыты и реализация зафиксирована, выполняется `/openspec archive`, затем слияние в `main` по разделу 3.4. Архивация OpenSpec и Git-слияние — отдельные операции.
5. **Прагматизм**: Для мелких технических правок и служебных скриптов артефакты OpenSpec не дублируются, если решение уже детально согласовано с пользователем в диалоге. Такие правки также выполняются в отдельной ветке с проверками и ревью перед коммитом.

## 5. Гигиена инструментов агента (Tool Hygiene)

1. **Переносимость**: Использовать доступные инструменты агента; правила проекта не зависят от названий конкретных инструментов редактирования.
2. **Хирургическая точечность изменений**: Для редактирования существующих файлов использовать компактные точечные правки вместо полной перезаписи без необходимости.
3. **Сохранение документации**: Не удалять существующие комментарии, докстринги и пояснения в коде без явной необходимости.
4. **Тихий вывод команд (Quiet by default)**: Команды тестов и линтеров должны запускаться с флагами тишины (например, `pytest -q`, `ruff check .`). При успехе — минимум вывода, при сбое — только ошибки.
5. **Новая сессия**: Прочитать ROADMAP, активные изменения, нужные `openspec/specs/` и связанный дизайн, включая архив. Принятые решения менять только после обсуждения.
6. **Однократность проверок перед ревью**: Проверки лимита символов, форматирования, линтинга и тестов выполняются строго однократно в финальном блоке перед ревью. Запрещено циклически вызывать скрипты проверок и ручные замеры после каждого промежуточного действия.

---

## 6. Протокол проверки Zero-Defect

Все команды проекта выполняются в изолированном `venv`, а после подготовки Docker допускается запуск внутри соответствующего контейнера. Зависимости устанавливаются только в эти окружения; установка в системный Python или глобально на машине запрещена. Команды ниже приведены для активированного `venv` или запуска внутри контейнера из корня проекта.

Перед остановкой на ревью и коммитом агент обязан в тихом режиме выполнить проверки:
1. **Проверка лимита символов**:
   ```bash
   python3 scripts/check_limits.py
   ```
2. **Линтинг и форматирование (Ruff)**:
   ```bash
   ruff check .
   ruff format --check .
   ```
3. **Автоматические тесты (pytest)**:
   ```bash
   pytest -q
   ```

Все автопроверки выполняются молча. При успешном прохождении их результаты в сводку ревью не дублируются (без простыней текста и логов). При падении тестов или линтеров агент обязан самостоятельно устранить ошибки до показа сводки ревью.

До появления основы приложения и виртуального окружения на этапе 05 вызовы `ruff` и `pytest` в консоли не производятся. После появления окружения на этапе 05 линтинг и тесты становятся строго обязательными.
