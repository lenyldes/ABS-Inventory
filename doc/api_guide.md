# Руководство по API проекта ABS Inventory

Документ содержит обзор публичных HTTP эндпоинтов системы и правила взаимодействия.

## Общие соглашения

- **Формат данных**: `application/json` (кодировка UTF-8).
- **Даты и время**: формат ISO 8601 (`YYYY-MM-DD` для дат, `YYYY-MM-DDTHH:MM:SSZ` для меток времени).
- **Часовой пояс**: по умолчанию все даты актуальности и списаний рассчитываются в поясе `Europe/Moscow`.
- **Числовая точность**: объёмы и остатки — `Decimal` с точностью 0,001; цены и суммы — `Decimal` с точностью 0,01 рубля с округлением `ROUND_HALF_UP`.
- **Строгая валидация**: передача необъявленных полей запрещена (`extra="forbid"`).

## 1. Складской учёт и остатки

- **POST `/api/movements/receipt`**: приёмка новой партии товара на склад (фиксация партии, срока годности и закупочной цены).
- **POST `/api/movements/consume`**: списание товара на спа-процедуры по правилу FEFO (в первую очередь партии с минимальным сроком годности).
- **POST `/api/movements/write-off`**: списание брака, повреждений или истёкшего срока годности.
- **POST `/api/movements/transfer`**: парное перемещение между объектами (расход с источника, приход на получатель).
- **POST `/api/movements/return`**: возврат поставщику партии товара.
- **GET `/api/stock`**: актуальные физические и доступные (годные) остатки в разрезе товаров, складов и партий.

---

## 2. Исправления и аудит движений

Подробная спецификация приведена в [контрактах API исправлений и аудита](api/movement-amendments.md).

- **POST `/api/amendments/preview`**: симуляция применения правок или отмены операций задним числом с расчётом влияния на складские остатки без сохранения.
- **POST `/api/amendments/confirm`**: атомарное подтверждение правок с транзакционной блокировкой и защитой от конфликтующих параллельных операций (`409 Conflict`).
- **GET `/api/movements/{id}/history`**: хронологическая цепочка аудита версий складского документа.

---

## 3. Прогнозирование потребности и предупреждения о рисках

- **POST `/api/forecast`**: расчёт среднесуточного расхода (за 90 дней), даты исчерпания запаса, точки заказа и одной рекомендации на выбранный горизонт по конкретной паре «товар + объект».
- **GET `/api/alerts`**: оперативный список рисков и дефицитов по каталогу (критический остаток, скорое исчерпание, просроченные партии, задержанные заказы).

## 4. План повторных закупок и бюджет

Подробная спецификация, описание алгоритма и расширенный пример приведены в [контракте API плана закупок](api/procurement-plan.md).

### Эндпоинт POST `/api/procurement/plan`
Формирует расчётный (не сохраняемый в БД) план последовательных пополнений нескольких товаров на скользящий горизонт (1, 3, 6 или 12 месяцев) и агрегирует проверяемый бюджет по календарным месяцам, артикулам, категориям и складам.

**Ключевые концепции**:
- **Скользящий горизонт**: период потребности начинается на следующий день после `as_of` (`as_of + 1`) и заканчивается на `as_of + horizon_months` со сдвигом на последний день месяца. Дата заказа `as_of` входит в бюджетный период.
- **Бюджетные месяцы (`is_partial`)**: позиции группируются по календарному месяцу даты размещения заказа. Неполные начальный и конечный месяцы помечаются флагом `is_partial = True`.
- **Группа «без даты» (`undated`)**: позиции товаров без срока поставки формируются как недатированные оценки потребности на весь горизонт и выносятся в отдельную группу `budget.undated`.
- **Информационный лимит бюджета (`budget_limit`)**: не изменяет и не обрезает рекомендации плана. Возвращает статус `within`, `exceeded` или `undetermined` (если есть позиции без цен).
- **Исключение оформленных заказов**: ранее оформленные неполученные заказы (`existing_orders`) покрывают ранний расход и исключены из стоимости новых закупок.
