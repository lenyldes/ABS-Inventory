# Техническая инструкция: Демонстрационный набор данных (app.demo_data)

Документ описывает назначение, порядок запуска, правила безопасной пересборки и сквозной маршрут проверки демонстрационного набора данных проекта **ABS Inventory & Procurement Assistant** (этап 09 ROADMAP). Инструкции для конечных пользователей и пользовательский интерфейс будут включены в `README.md` на этапе 13.

---

## 1. Назначение и состав набора

Демонстрационный набор предназначен для воспроизводимой проверки всей аналитической цепочки системы: складского учета, расчета среднедневного расхода, прогнозирования спроса, выявления рисков и формирования квартального плана закупок со сведением бюджета.

### Основные характеристики
- **Изоляция ключей**: все синтетические сущности имеют стабильный деловой префикс `DEMO-` (объекты, товары, поставщики, партии, документы).
- **Привязка к контрольной дате (`as_of`)**: все исторические движения, сроки годности партий и ожидаемые заказы вычисляются как фиксированные смещения от заданной даты актуальности.
- **Объекты и поставщики**:
  - Объекты: `DEMO-MS-01` (Основной салон) и `DEMO-MS-02` (Загородный клуб).
  - Поставщики: `DEMO-SUP-MAIN` (Основной поставщик) и `DEMO-SUP-ALT` (Альтернативный поставщик).
- **Складской граф**: остатки формируются исключительно через штатные складские операции (`register_receipt`, `register_consume`) с фиксацией версий, партий и распределений FEFO.
- **Покрытие 9 SKU**: помимо целевого сценария массажного масла, набор покрывает 8 пограничных ситуаций (дефицит, просрочка, риск списания, неликвид, неполная история, отсутствие цены, отсутствие условий поставщика, заказ в пути).

## 2. CLI-команда и режимы управления

Подготовка и управление демонстрационным набором выполняются через CLI-модуль `app.demo_data`.

### Синтаксис запуска

Локально:
```bash
python -m app.demo_data --as-of YYYY-MM-DD [--replace]
```

Через Docker Compose:
```bash
docker compose run --rm app python -m app.demo_data --as-of YYYY-MM-DD [--replace]
```

### Параметры
- `--as-of YYYY-MM-DD` (*обязательный*): контрольная дата актуальности набора. Дата не может быть в будущем относительно текущей календарной даты в часовом поясе `Europe/Moscow`. При невалидной или будущей дате команда немедленно завершается с кодом 1 без изменения БД.
- `--replace` (*опциональный*): явное разрешение на замену существующего демонстрационного набора данных.

## 3. Правила выполнения и безопасность данных

### 3.1. Первичная подготовка
При первом запуске на чистой БД в единой транзакции создаются справочники, проводятся 105 складских движений и регистрируется ожидаемый заказ. При любом сбое выполняется полный откат (`ROLLBACK`), частичное создание исключено.

### 3.2. Идемпотентный повтор
Повторный запуск команды с той же датой `--as-of` без флага `--replace`:
- Определяет дату существующего набора по опорному приходу `DEMO-REC-OIL-BASE` (на `as_of - 100 дней`).
- Сверяет полный перечень деловых ключей `DEMO-` в БД.
- Если набор цел и дата совпадает, команда завершается успешно со статусом `повтор (без изменений)` (no-op). Никакие записи не изменяются и не дублируются.
- Если передана иная дата без `--replace`, команда завершается с ошибкой и требует указать `--replace`.
- Если обнаружен неполный набор (удалены строки) или лишние записи с префиксом `DEMO-`, запуск блокируется с ошибкой нарушения целостности набора.

### 3.3. Изолированная пересборка (`--replace`)
Флаг `--replace` позволяет пересобрать набор на новую дату (или принудительно обновить текущую):
1. **Проверка внешних зависимостей (Pre-check)**:
   - Проверяется отсутствие сторонних складских движений, партий, заказов или условий поставщиков, ссылающихся на демотовары, демообъекты или демопоставщиков.
   - Проверяется отсутствие строк исправлений (`AmendmentEntry`) на демодвижения.
   - При наличии хотя бы одной внешней ссылки пересборка немедленно отклоняется с ошибкой до удаления данных.
2. **Точечная очистка демографа**:
   - Удаляются только собственные записи демонабора в строгом обратном порядке внешних ключей (версии движений, распределения, движения, партии, заказы, блокировки остатков, условия, справочники).
   - Пользовательские и системные записи за пределами ключей `DEMO-` не затрагиваются.
3. **Атомарная загрузка**:
   - Новый набор формируется со смещениями относительно новой даты в той же транзакции. При ошибке восстанавливается исходное состояние.

## 4. Сквозной демонстрационный маршрут

Основная контрольная дата для эталонных сценариев: `2026-09-29`.

### Шаг 1. Контроль складских остатков масла
- **Запрос**: `GET /api/stock?as_of=2026-09-29&limit=100`
- **Объект и товар**: `DEMO-OIL` на складе `DEMO-MS-01`.
- **Эталонные показатели**:
  - `current_stock`: `50.000` (приход 140 на день `-100`, 90 ежедневных списаний по 1 на дни `-89…0`).
  - `available_stock`: `50.000` (заблокированных остатков нет).
  - `expired_stock`: `0.000`.
  - `average_daily_consumption`: `1.000000` (90 единиц за 90-дневное расчетное окно).
  - `days_of_stock`: `50.000` дней.
  - `nearest_expiry_date`: `2026-12-18` (партия годна еще 80 дней).

### Шаг 2. Расчет прогноза потребления и потребности
- **Запрос**: `POST /api/forecast`
- **Тело запроса**:
  ```json
  {"sku": "DEMO-OIL", "location": "DEMO-MS-01", "as_of": "2026-09-29", "horizon_days": 90}
  ```
- **Результат**:
  - Среднедневной расход: `1.000000`.
  - Текущий остаток: `50.000`.
  - Ожидаемый расход за 90 дней: `90.000`.
  - Расчет точки заказа с учетом срока поставки (7 дней).

### Шаг 3. Мониторинг предупреждений и пограничных рисков
- **Запрос**: `GET /api/alerts?as_of=2026-09-29&limit=100`
- **Демонстрация спектра рисков на едином наборе**:
  - `lead-time-stockout`: SKU `DEMO-DEFICIT` (`DEMO-MS-02`), остаток 5 при расходе 90, срок поставки 10 дней — исчерпание запаса до даты поставки.
  - `expiry-and-writeoff`: SKU `DEMO-EXPIRY` (`DEMO-MS-01`), остаток 30, срок годности истекает через 5 дней — риск списания.
  - `expired-stock`: SKU `DEMO-EXPIRED` (`DEMO-MS-01`), остаток 10 просрочен (`expired`), доступный остаток равен 0.
  - `no-movement`: SKU `DEMO-IDLE` (`DEMO-MS-01`), отсутствие расхода свыше 90 дней (неликвид).
  - `short-history`: SKU `DEMO-SHORT` (`DEMO-MS-02`), история движений всего 10 дней (`history_days = 10`), средний расход считается как `1 / 90`.

### Шаг 4. Квартальный план закупок и сведение бюджета
- **Запрос**: `POST /api/procurement/plan`
- **Тело запроса**:
  ```json
  {"as_of": "2026-09-29", "horizon_months": 3}
  ```
- **Закупка масла `DEMO-OIL`**:
  - Дата заказа: `2026-11-11` (с учетом 7 дней срока поставки к исчерпанию на 50-й день `2026-11-18`).
  - Количество к заказу: `30.000` (с учетом размера упаковки 5 и минимального заказа 10).
  - Цена за единицу: `100.00` руб.
  - Стоимость позиции: `3000.00` руб.
- **Обработка особых условий в плане**:
  - `DEMO-NOPRICE`: рассчитана потребность, но отсутствует цена поставщика (`unit_price: null`, `total_cost: null`, признак неполноты бюджета).
  - `DEMO-NOLEAD`: отсутствуют закупочные условия (`SupplierCondition`), позиция попадает в недатированные (`undated`) с пояснением причины.
  - `DEMO-INCOMING`: ожидаемая поставка `DEMO-PO-INCOMING` (+1 день, 20 шт.) исключает повторный заказ на ближайший горизонт.
  - `DEMO-IDLE`: неликвид исключен из плана закупки (заказ 0).
- **Сведение аналитических разрезов бюджета**:
  - Итоговая подтвержденная сумма (`known_total`): `20300.00` руб.
  - Итоговое подтвержденное количество (`total_quantity`): `203.000` шт.
  - Все бюджетные разрезы сходятся с единым списком позиций: по месяцам (`by_month` + `undated`), по SKU (`by_sku`), по категориям (`by_category`), по объектам (`by_location`).

## 5. Каталог эталонных сценариев (`app.demo_data.scenarios`)

Каталог `DEMO_SCENARIOS` фиксирует стабильные машиночитаемые эталоны:

| ID сценария | Метод и путь API | Цель сценария | Ключевые эталонные показатели |
|---|---|---|---|
| `oil-quarter-plan` | `POST /api/procurement/plan` | Целевой план закупки масла | Дата `2026-11-11`, кол-во `30`, цена `100.00`, стоимость `3000.00`, бюджет `20300.00` |
| `lead-time-stockout` | `GET /api/alerts` | Дефицит до поставки | Тип `stockout`, дата исчерпания, дни дефицита |
| `expiry-and-writeoff` | `GET /api/alerts` | Риск скорого списания | Тип `expiring_soon`, `writeoff_risk`, объем партии |
| `expired-stock` | `GET /api/stock` | Просроченный остаток | Тип `expired`, учтенный остаток `10.000`, доступный `0.000` |
| `no-movement` | `GET /api/alerts` | Неликвидный товар | Тип `no_movement`, нулевой заказ в плане закупок |
| `short-history` | `POST /api/forecast` | Неполная история | Тип `incomplete_history`, `history_days = 10`, расход `1/90` |
| `unknown-price` | `POST /api/procurement/plan` | Потребность без цены | Позиция сформирована, `unit_price: null`, `total_cost: null` |
| `unknown-lead-time` | `POST /api/procurement/plan` | Потребность без условий | Недатированная позиция в `undated`, зафиксирована причина |
| `incoming-order` | `POST /api/procurement/plan` | Учет ожидаемой поставки | Учтен `DEMO-PO-INCOMING`, дублирующий заказ отсутствует |
