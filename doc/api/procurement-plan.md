# Контракт API плана повторных закупок и бюджета

Документ описывает публичный HTTP API расчёта плана повторных закупок и детализированного бюджета: `POST /api/procurement/plan`.

Полный развёрнутый пример ответа с демонстрационными данными см. в [демонстрационном примере](procurement-plan-example.md).

## 1. Назначение и принципы работы

1. **Детерминированный расчёт без записи**: эндпоинт выполняет расчёт в транзакции с уровнем изоляции `REPEATABLE READ`, гарантируя согласованный снимок остатков, истории и заказов. План является чисто расчётным и не создаёт записей и движений в БД.
2. **Последовательные пополнения**: в отличие от одиночной оценки `/api/forecast`, план моделирует последовательные пополнения с шагом в один календарный месяц на протяжении всего горизонта, учитывая сроки поставок, минимальный заказ и кратность упаковок.
3. **Сверяемый бюджет**: все аналитические разрезы (по месяцам, SKU, категориям, объектам и недатированная группа) рассчитываются из одного неизменяемого набора сформированных позиций.

---

## 2. Параметры запроса (POST /api/procurement/plan)

Тело запроса передаётся в формате JSON:

| Поле | Тип | Обязательное | Значение по умолчанию | Описание |
|---|---|---|---|---|
| `as_of` | date (`YYYY-MM-DD`) | Нет | Сегодня (`Europe/Moscow`) | Контрольная дата актуальности расчёта |
| `horizon_months` | int | **Да** | — | Горизонт планирования: строго `1`, `3`, `6` или `12` |
| `service_days` | int | Нет | `0` | Дни целевого страхового запаса ($\ge 0$) |
| `location` | str | Нет | `null` | Фильтр по коду объекта/склада (например, `"LOC-MSK"`) |
| `category` | str | Нет | `null` | Фильтр по категории товара (например, `"Масла"`) |
| `budget_limit` | decimal | Нет | `null` | Информационный лимит бюджета в рублях ($\ge 0.00$) |

*Примечание*: передача неизвестных полей запрещена (`extra="forbid"`). При отсутствии фильтров рассчитываются все товары каталога по всем объектам.

## 3. Концепции календаря и бюджета

### 3.1. Скользящий горизонт
- **Границы потребности**: интервал потребности начинается на следующий день после даты актуальности (`horizon_start = as_of + 1 день`) и завершается на дату `as_of + horizon_months` со сдвигом на последний день месяца (`horizon_end`).
- Например, при `as_of = 2026-09-15` и `horizon_months = 3` горизонт охватывает интервал с `2026-09-16` по `2026-12-15` (91 день).
- Дата заказа `as_of` входит в бюджетный период, позволяя зафиксировать немедленный заказ в первый месяц.

### 3.2. Бюджетные месяцы и признак неполного месяца (`is_partial`)
- Позиции группируются в `budget.by_month` по календарному месяцу даты размещения заказа (`order_date.strftime("%Y-%m")`).
- Каждый месяц содержит признак `is_partial: bool`:
  - `is_partial = True`, если месяц начинается не с 1-го числа (первый месяц при `as_of.day != 1`) или заканчивается не в последний день месяца (последний месяц при `horizon_end.day != last_day`).
  - `is_partial = False` для полных календарных месяцев внутри горизонта.

### 3.3. Группа «без даты» (`undated`)
- Если для товара не указан срок поставки (`lead_time_days = None` в условиях поставщика), невозможно смоделировать точную дату прихода и FEFO-остаток по дням.
- Для таких позиций формируется одна недатированная оценка потребности на весь горизонт (по формуле одиночного прогноза).
- Недатированные позиции выделяются в группу `budget.undated` (`is_undated: true`, `order_date: null`) и не включаются ни в один календарный месяц.
- **Баланс бюджета**: `budget.known_total = sum(by_month.known_total) + undated.known_total`.

## 4. Ограничения и бизнес-правила

1. **Информационный характер лимита бюджета (`budget_limit`)**:
   - Лимит не изменяет и не обрезает рекомендации: все необходимые закупки сохраняются в ответе в полном объёме.
   - Статус лимита (`limit_status`):
     - `within`: известная сумма не превышает лимит (`known_total <= budget_limit`), и все цены полностью определены (`is_price_complete = true`).
     - `exceeded`: известная сумма строго превышает установленный лимит (`known_total > budget_limit`).
     - `undetermined`: известная сумма $\le$ лимита, но есть хотя бы одна позиция с неопределённой ценой (`is_price_complete = false`), поэтому итоговые затраты могут превысить лимит.
   - Разница: `limit_difference = known_total - budget_limit`.
2. **Исключение оформленных заказов из новых затрат**:
   - Ранее оформленные неполученные заказы поставщикам (`purchase_orders`) возвращаются в блоке `existing_orders`.
   - Они участвуют в расчёте как входные поставки и отодвигают потребность в новых заказах.
   - Их стоимость **не входит** в `budget.known_total` и новые позиции, исключая двойной учёт затрат.
3. **Неполные данные и предупреждения**:
   - **Отсутствие цены**: если нет фактических приходов и ориентировочной цены поставщика, позиция формируется с `unit_price: null`, `total_cost: null` и предупреждением. В бюджете увеличивается счётчик `unpriced_items_count`.
   - **Временный дефицит (`TEMPORARY_DEFICIT`)**: если остаток исчерпывается до даты прихода ближайшего заказа, заказ предлагается на `as_of`, а необеспеченные дни отмечаются предупреждением с точным интервалом (`дефицит с YYYY-MM-DD до YYYY-MM-DD`). Товар не считается прибывшим раньше срока.
   - **Задержанные заказы (`ORDER_DELAYED`)**: ожидаемые заказы с датой $\le as\_of$ исключаются из покрытия до уточнения даты.
   - **Поставка за горизонтом (`DELIVERY_BEYOND_HORIZON`)**: если дата поставки выходит за конец горизонта, заказ внутри горизонта не создаётся.

## 6. Коды ответов и ошибки

- **`200 OK`**: Успешный расчёт плана и бюджета.
- **`400 Bad Request`**:
  - `horizon_months` не равен 1, 3, 6 или 12.
  - `service_days < 0`.
  - `budget_limit < 0.00`.
- **`404 Not Found`**:
  - Указанный `location` не найден в справочнике складов.
  - Указанная `category` отсутствует среди категорий товаров.
- **`422 Unprocessable Entity`**:
  - Неверные типы данных или невалидный формат дат.
  - Переданы недопустимые лишние поля запроса (`extra="forbid"`).
