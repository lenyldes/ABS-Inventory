# Design

## Context

Первая версия сайта, её запуск и демонабор описаны в `initial-design.md`. Сейчас `web/index.html` показывает подробные разделы склада, журнала и аналитики, а `web/js/api.js` скрывает исходный HTTP-статус и тело ошибки от вызывающего кода. Новый маршрут проверки строится на существующих API и общем томе БД. Точные контрольные примеры вынесены в `verification-cases.md`.

## Goals / Non-Goals

**Goals:** дать человеку без технической подготовки готовые действия с реальными запросами, ответами и понятными выводами; сохранить подробные экраны и малый размер модулей.

**Non-Goals:** новые API и миграции, отдельная БД или сеанс на посетителя, сброс общего набора, чат, публикация стенда и клиентский `README.md`.

## Decisions

### Проверка задания


Новый первый экран в `web/index.html` ведёт по карточкам обязательных возможностей; подробные разделы остаются ниже. `web/js/main.js` после `/api/demo/status` передаёт `state.asOf` в `initVerification()`; отдельная проверка не запускает запросы автоматически. `web/js/verification-read.js` и `web/js/verification-write.js` хранят небольшие группы построителей запросов и извлечения ключевых полей по `verification-cases.md`. `web/js/verification.js` управляет кнопками, последовательными шагами, состояниями и DOM. `web/js/api.js` получает общий низкоуровневый обмен, который возвращает фактические метод, URL, тело запроса, HTTP-статус и JSON ответа как для 2xx, так и для ошибок; прежние `getJson`, `postJson`, `getAllPages` сохраняют сигнатуры и поведение. Карточка выводит только обмены своего нажатия, не фоновый трафик склада.

Контракт нового клиента: `exchangeJson(method, path, {params, body, signal})` возвращает `{request: {method, url, body}, response: {status, body}, error}`; для HTTP 4xx `error=null` и сохраняется JSON, для сетевого сбоя `status=null`, для ошибки разбора сохраняется HTTP-статус и `error.kind="invalid_json"`. `request.url` — относительный путь с сериализованными query-параметрами, `body=null` для GET. Адаптеры `getJson`/`postJson` поверх этого обмена сохраняют существующий `ApiError`. В `verification.js` каждый запуск создаёт собственный список обменов и передаёт его рендеру карточки; начальное состояние не содержит фиктивного ответа. `verification-read.js` получает `asOf` и возвращает набор готовых шагов; `verification-write.js` получает дату Москвы и идентификатор запуска, ведёт зависимые шаги и отдаёт данные для вывода, не обращаясь к DOM.

Для записи JS генерирует короткий случайный идентификатор и документы `CHECK-*` для `OIL-001`/`MS-01`; UI не изменяет `DEMO-`. Каждый успешный шаг записи обновляет существующие склад и журнал через точку подключения `warehouse.refreshAfterMovement()`. Связанные шаги (`receipt` → `consume`, первый документ → `409`) выполняются по очереди; при сбое первого второй не отправляется. Результат FEFO строится по реальным `allocations` и `GET /api/stock/OIL-001`, без обещания фиксированной партии после повторов на общей БД. `web/styles.css` оформляет четыре колонки цепочки и состояния; `scripts/test_web_ui_e2e.sh` проверяет HTTP-обмен через прокси, а `doc/ui-demo.md` после стабилизации описывает нажатия и ожидаемые признаки.

Альтернатива — отдельный backend сеансов или копия БД на посетителя — отклонена после согласования общего набора: это меняло бы API и эксплуатацию. Альтернатива — показывать заранее заготовленный JSON — не доказывает работу сервера. Новых API-маршрутов, миграций и зависимостей нет. Точные входы и выходы чистого стенда: `verification-cases.md`.

## Risks / Trade-offs

- Общая БД накапливает документы → номера уникальны, числовые остатки записывающих шагов берутся из ответа; точные эталоны применяются только в изолированном Compose-тесте.
- Публичный API позволяет изменить `DEMO-` вне сайта → карточка показывает расхождение факта с эталоном; ограничение публичного стенда остаётся предметом этапа 12.
- Клиент может не получить ответ после успешной записи → повтор создаёт новый документ и явно показывает фактический результат; автоматического скрытого повтора POST нет.

## Migration Plan

Миграция данных не нужна. Сайт использует прежние относительные API-пути и тот же Compose-стек; откат возвращает прежние статические файлы сайта. Записи проверок в общей БД остаются как обычные движения.
