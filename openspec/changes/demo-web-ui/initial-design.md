# Design

## Context

Этот документ сохраняет решения первой версии сайта. Доработка маршрута проверки задания описана в `design.md` и `verification-cases.md`.

См. `proposal.md` и delta-спецификации. На момент первой версии `docker-compose.yml` запускал `db`, `app`, `test`, а полный `DEMO-` набор создавался отдельно. Сейчас Compose запускает также `web`, демонабор готовится при первом старте, сайт показывает склад, журнал, прогноз и план, но не ведёт проверяющего по требованиям задания. Дата набора определяется по опорному движению `DEMO-REC-OIL-BASE`. Каталожного API нет; для начального выбора SKU/объекта используется `GET /api/stock`.

## Goals / Non-Goals

**Goals:** один адрес сайта для проверяющего; структура страниц и обмен с API без самостоятельных расчётов в браузере; безопасный повторный запуск с сохранением БД; небольшие файлы и последовательные проходы реализации.

**Non-Goals:** новый каталог API, изменение складских/расчётных контрактов, сброс данных посетителей, чат, авторизация, публикация на сервере и клиентский `README.md` (этапы 11–13).

## Decisions

### 1. Подготовка данных и дата снимка

Новый `app/demo_data/bootstrap.py` выполняется в команде `app` после миграций и сидов, до Uvicorn. Он открывает сессию через `get_session_factory()`. Если `get_existing_demo_keys()` не находит ни одного ключа, вызывает `prepare_demo_data(session, today_in_moscow())`; существующая транзакция загрузчика остаётся единственной операцией записи. Если ключи есть, вызывает `verify_demo_keys()` и `detect_demo_as_of()`, затем завершается без записи. Отсутствующая опорная запись или неполный набор дают ненулевой код и прерывают старт. Повтор не сверяет значения каждой записи и не пересоздаёт набор: дата и пользовательские изменения сохраняются. Вывод ошибки не содержит строки подключения. CLI `app.demo_data.__main__` не меняется.

Новый читающий `app/api/demo_status.py` получает сессию через `get_db`, проверяет наличие и структуру ключей, возвращает `{"ready": true, "as_of": "YYYY-MM-DD"}` по `detect_demo_as_of()`; при отсутствии/неполноте отвечает `503`, не вызывая загрузчик. `app/main.py` подключает маршрут. Это отдельный маршрут, поскольку дата исходного набора должна оставаться доступной после перезапуска и отличаться от текущей даты. Альтернатива — искать опорный документ через пагинированный журнал; она связывает UI с внутренним устройством фикстуры и требует лишних запросов.

### 2. Отдельный статический сервис

`web/Dockerfile` собирает `nginx:alpine` с `web/nginx.conf` и статическими файлами. В `docker-compose.yml` сервис `web` публикует `${WEB_PORT:-8080}:80`, ждёт healthcheck `app` на `/health`; `app` остаётся на `${PORT:-8000}:8000` для прямой проверки API. Nginx отдаёт `/`, а `/api/`, `/docs`, `/openapi.json` и `/health` проксирует в `app:8000` без изменения пути. Браузер использует относительные URL; CORS и сборка Node не нужны. В `.env.example` добавить `WEB_PORT`. Альтернатива — React/Vite: добавляет сборку и зависимости без необходимости для единой страницы. Публикация домена и внешний HTTPS относятся к этапу 12.

### 3. Поток данных интерфейса

После загрузки `web/js/main.js` запрашивает `/api/demo/status`, устанавливает неизменяемую для сеанса `as_of` из ответа и запускает чтение склада, предупреждений и плана на 3 месяца. `web/js/api.js` содержит `fetch` с разбором успешного JSON и унифицированных ошибок (`message`, `details.errors`), а также пагинацию списка до `total`; ошибки не подменяются пустым результатом. `web/js/state.js` хранит выбранные `sku`, `location`, `category`, горизонт, `service_days`, `budget_limit`, состояние запроса; устаревший ответ не должен заменять результат нового пересчёта.

`web/js/warehouse.js` показывает строки склада, выбор пары, `GET /api/stock/{sku}?location=...&as_of=...`, журнал `GET /api/movements` с фильтрами/страницами и `allocations`; статус партии вычисляется из ответа API и даты снимка только для подписи, количество не пересчитывается. `web/js/analytics.js` показывает `GET /api/alerts`, `POST /api/forecast` для выбранной пары и `POST /api/procurement/plan` для фильтров. Горизонты плана: только 1/3/6/12 месяцев; для одиночного прогноза тот же `horizon_months`. План, бюджетные разрезы, `existing_orders`, `explanation`, `warnings` отображаются из одного ответа. Для `null` выводится «Нет данных»; `known_total` подписан как известная часть при `is_price_complete=false`, `undated` выделен отдельно. Фильтры применяются кнопкой «Пересчитать», а не на каждый ввод. Длинные `daily_forecast` и исходные формулы прячутся в раскрываемые секции.

`web/js/movement-form.js` строит поля по `MovementCreateRequest`: общие дата (сегодня по Москве), SKU, объект, тип, количество, `doc_number`; для `receipt` — `batch_number`, `expiry_date`, `unit_price`, опциональный `supplier_id`; для `writeoff`/`correction` — `batch_id`, `reason`; для `return` — `parent_movement_id`, `parent_allocation_id`, опциональная причина. `consume` не выбирает партию. Связанные ID берутся из видимых партий, движений и `allocations`, но допускается ручной ввод для проверки API. Отправляется только разрешённый для типа набор полей. Проверка `sku.startsWith('DEMO-')` блокирует отправку до `fetch`; `OIL-001` и `MS-01` предложены как значения для теста. После 201 показываются `id`, остатки, `allocations`, обновляются склад и журнал; ошибки API остаются рядом с формой. Эта защита действует только в UI, публичный API не меняется.

`web/index.html` содержит навигацию по пяти участкам, компактные формы, области результатов, ссылку на `/docs` и заглушку AI. `web/styles.css` задаёт адаптивную верстку и различимые состояния загрузки/ошибки/неполной цены. Серверный рендеринг, библиотека компонентов и локальное хранение данных не требуются.

### 4. Проверка и техническая инструкция

`tests/test_demo_bootstrap.py` покрывает пустой набор, повтор на следующую дату, неполные ключи и сохранение пользовательских записей. `tests/test_api_demo_status.py` покрывает 200/503. `tests/test_compose_lifecycle.py` и `scripts/test_compose_lifecycle.sh` обновляются под автоматический набор: прежнее ожидание ровно трёх сидовых SKU неверно. Новый `scripts/test_web_ui_e2e.sh` в изолированном Compose-проекте проверяет страницу и прокси, статус с датой, остаток `DEMO-OIL`, риски и квартальный план. В `scripts/check.sh` он добавляется как обязательная проверка. Поведение браузерных переходов, раскрытия объяснений и формы проверяется вручную по `doc/ui-demo.md`; в репозитории нет браузерного раннера, и добавлять его ради одной страницы не требуется.

| Файл | Действие и назначение |
|---|---|
| `app/demo_data/bootstrap.py` | Новый запуск подготовки без явной CLI-даты при пустом наборе |
| `app/api/demo_status.py`, `app/main.py` | Новый маршрут и его подключение |
| `docker-compose.yml`, `.env.example` | Команда запуска, `web`, healthcheck и порт |
| `web/Dockerfile`, `web/nginx.conf` | Отдельный образ и прокси |
| `web/index.html`, `web/styles.css` | Разметка и адаптивные состояния |
| `web/js/api.js`, `web/js/state.js`, `web/js/main.js` | HTTP, состояние и запуск сценария |
| `web/js/warehouse.js`, `web/js/analytics.js`, `web/js/movement-form.js` | Склад, расчёты и форма операций |
| `tests/test_demo_bootstrap.py`, `tests/test_api_demo_status.py` | Автоподготовка и статус |
| `tests/test_compose_lifecycle.py`, `scripts/test_compose_lifecycle.sh` | Повторный запуск с сохранением набора |
| `scripts/test_web_ui_e2e.sh`, `scripts/check.sh` | Сквозная проверка сайта в общем гейте |
| `doc/ui-demo.md` | Технический маршрут запуска и ручной проверки; после стабилизации поведения |

## Контрольные примеры

| Условие / запрос | Ожидаемый результат |
|---|---|
| Чистая БД, Москва `2026-09-29`, `docker compose up` | `GET /api/demo/status` → 200, `ready=true`, `as_of=2026-09-29`; после перезапуска дата та же, набор не удвоен |
| `GET /api/stock?as_of=2026-09-29&limit=100`, пара `DEMO-OIL`/`DEMO-MS-01` | `current_stock=50.000`, `available_stock=50.000`, `average_daily_consumption=1.000000`, `days_of_stock=50.000` |
| `GET /api/stock/DEMO-EXPIRED?as_of=2026-09-29` | Учётный остаток 10.000, доступный 0.000 |
| `POST /api/procurement/plan` с `{"as_of":"2026-09-29","horizon_months":3}` на контрольном наборе | Позиция `DEMO-OIL`/`DEMO-MS-01`: дата заказа `2026-11-11`, 30.000, 3000.00 руб.; известная часть бюджета 20300.00 руб. |
| Форма `receipt` для `OIL-001`/`MS-01`, `quantity=2.000`, новый `doc_number`, партия и цена | 201; новый остаток и документ видны в форме, складе и журнале |
| Форма с `sku=DEMO-OIL` | HTTP-запрос не выполняется, видна причина запрета |

Последний бюджетный эталон сверяется на наборе без посторонних платных закупок; на постоянно работающем стенде результаты могут измениться из-за действий через публичный API. Все точные числа уже зафиксированы в `app.demo_data.scenarios` и проверяются существующим `tests/test_demo_data_api.py`.

## Risks / Trade-offs

- Публичный `POST /api/movements` позволяет обойти ограничение формы и изменить общий снимок → UI защищает контрольный маршрут от случайной правки; ограничения публичного API и восстановление стенда рассматриваются на этапе 12.
- Дата набора остаётся прежней после перезапуска через дни → сайт явно показывает `as_of` и использует её во всех аналитических запросах.
- Nginx может отдать HTML раньше готовности API при сбое запуска → UI показывает ошибку; `web` ожидает здоровый `app` при штатном старте.
- Новые пути Compose могут сломать существующие сквозные проверки → обновить ожидания и проверить на изолированных проектах через единый `scripts/check.sh`.

## Migration Plan

Миграция схемы БД не нужна. На чистом томе демонабор создаётся автоматически; на существующем томе без `DEMO-` он добавляется при первом старте новой версии, остальные записи сохраняются. Для отката возвращаются прежние команда `app` и Compose-конфигурация; созданный демонабор остаётся в БД и может быть удалён только штатной явной процедурой управления данными.
