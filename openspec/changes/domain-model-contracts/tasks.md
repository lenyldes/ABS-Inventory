# Задачи этапа 04

Это документационное изменение. Задачи ниже завершают модель и контракты; реализация приложения относится к отдельным изменениям этапов 05–07. Наличие всех артефактов OpenSpec не означает закрытие этих задач.

## 1. Полнота предметных правил

- [x] 1.1 Сверить шесть спецификаций с согласованными решениями и ТЗ; результат — проверенное покрытие операций, ошибок, возвратов, исправлений и отмен со сценариями, без принятия всего БТ в объём.
- [x] 1.2 Согласовать порядок движений внутри одной даты и границы исторической проверки; дополнить сценариями позднего прихода и расхода в один день и одинаковых дат поступления/годности партий. Проверка — однозначный результат каждой последовательности.
- [x] 1.3 Уточнить допустимые количества и обязательные поля `writeoff`, `return`, `correction`, повторный номер отменённого документа и правила изменения даты/объекта/партии. Проверка — таблица валидации и сценарии связанного исправления, не меняющие уже согласованную семантику.

## 2. Детализация расчётных контрактов

- [x] 2.1 Согласовать порядок событий прогнозного дня, случай ожидаемой поставки на `as_of`, неизвестную годность будущих поставок и нового заказа, обработку неудовлетворённой потребности. Проверка — дневной пример с просрочкой и временным дефицитом, согласованный с итоговым объёмом заказа.
- [x] 2.2 Уточнить календарные месяцы на границе месяца, часовую зону даты «сегодня», точность промежуточных расчётов, денежное округление, горизонт поиска даты заказа при нулевом страховом запасе. Проверка — примеры конца месяца, нулевого расхода, нулевого страхового запаса и нехватки исходных данных.
- [x] 2.3 Зафиксировать семантику `current_stock`, `incoming_qty`, `stockout_date`, недоступных значений и горизонт предупреждений; описать, как определяется полнота 90-дневной истории. Проверка — согласованность ответов stock/forecast/alerts и отсутствие двойного учёта поставок на историческую дату.

## 3. Полные API-контракты

- [ ] 3.1 Описать точные поля, типы, обязательность, ограничения, фильтры, сортировку и пагинацию обязательных эндпоинтов в соответствующих спецификациях. Проверка — примеры успешных запросов/ответов и ошибок 400/404/409/422; неоднозначности поведения обсуждены до фиксации.
- [ ] 3.2 Описать маршруты и JSON-схемы предварительного просмотра и подтверждения набора исправлений, чтения истории и защиты от устаревшего/повторного подтверждения. Проверка — последовательности успешной правки, отказа по зависимости и конфликта после нового движения.
- [ ] 3.3 Уточнить способ подготовки и обновления справочников, закупочных условий и ожидаемых поставок в прототипе. Проверка — описан путь от начальных данных до частичной приёмки и изменения ожидаемого количества без обязательного внешнего интерфейса поставщика.

## 4. Проверка целостности и передача контекста

- [ ] 4.1 Сверить сущности, связи, конкурентные сценарии и API после детализации; выполнить `openspec validate domain-model-contracts --strict` и Zero-Defect. Проверка — нет противоречий, нарушений лимита и неоговорённых блокеров этапа 05; отсутствие тестов приложения отмечено честно.
- [ ] 4.2 Проверить восстановление контекста по AGENTS.md, ROADMAP, спецификациям и дизайну без переписки. Проверка — видны принятые решения, границы будущей реализации и все оставшиеся задачи; подготовлена сводка ревью перед отдельным подтверждением коммита.

Архивация выполняется только по отдельному запросу после завершения и фиксации задач. При архивации синхронизировать все шесть спецификаций, проверить их содержание и заменить ссылку ROADMAP на фактический путь архивного дизайна. Отметить этап 04 завершённым только после выполнения его критерия; затем отдельное ревью архива, подтверждённый коммит и подтверждённое слияние.
