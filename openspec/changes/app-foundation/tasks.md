# Задачи этапа 05: основа приложения

Работа выполняется небольшими частями с отдельным ревью и подтверждением перед каждым коммитом. Проверки Zero-Defect каждой завершённой части запускаются однократно в конце этой части.

## 1. Контейнерная среда, каркас и HTTP

- [x] 1.1 Создать пакеты модульного монолита, `requirements.txt` с точными прямыми версиями из `design.md`, Dockerfile на `python:3.11.16-slim-bookworm` и начальный Compose с `postgres:18.4`, приложением и именованным томом БД. Проверка: оба образа собираются, `pip check` и запуск контейнера проходят без установки пакетов на хост, каталог данных БД не попадает в репозиторий.
- [x] 1.2 Реализовать валидацию переменных окружения, подключение и сессию PostgreSQL, `GET /health` с `200`/`503` без секретов. Проверка: тесты покрывают рабочее и прерванное соединение, а также отсутствие обязательной конфигурации.
- [x] 1.3 Настроить закреплённые версии Ruff, pytest и httpx в образе, отдельную тестовую БД, `.env.example` и игнорирование локального `.env`. Проверка: контейнер сообщает согласованные версии инструментов, линтер и тесты выполняются через Compose, переменные соответствуют работающей конфигурации.

## 2. Полная предметная схема

- [x] 2.1 Создать ORM-модели справочников, закупочных условий и ожидаемых поставок с согласованными связями и точными типами. Проверка: тесты БД фиксируют уникальность деловых ключей, связи и точность Decimal.
- [x] 2.2 Создать модели партий, движений, распределений, исправлений, истории версий и `stock_locks`. Проверка: тесты БД фиксируют внешние ключи, частичную уникальность активного документа, точность количества и уникальность пары блокировки.
- [x] 2.3 Создать первую ревизию Alembic для всех моделей, без автоматического `create_all` при запуске. Проверка: миграция поднимает чистую PostgreSQL; повторный `upgrade head` не меняет данные; схема соответствует моделям.
- [x] 2.4 Уточнить в `design.md` назначение таблиц, миграции и пределы проверок БД по фактической схеме. Проверка: описание отличает ограничения схемы от правил FEFO и исторической обеспеченности этапа 06.

## 3. Начальные данные

- [x] 3.1 Создать небольшой детерминированный набор товаров, объектов, поставщиков и закупочных условий и идемпотентный загрузчик. Проверка: тест двух запусков сохраняет уникальные исходные записи и дополнительные пользовательские данные; партий и движений нет.

## 4. Контейнерный запуск и сквозная проверка

- [x] 4.1 Дополнить запуск Compose проверкой готовности PostgreSQL и последовательностью «миграция → сиды → HTTP». Проверка: `docker compose up` поднимает оба сервиса на пустом томе; сбой подготовки не даёт ложной готовности.
- [x] 4.2 Проверить `docker compose down` и повторный запуск, статусы `/health`, сохранение пользовательских записей в именованном томе и отсутствие дубликатов сидов. Проверка: интеграционный сценарий выполняется на отдельной тестовой БД или томе, не затрагивая рабочие данные.
- [x] 4.3 Завершить короткую инструкцию в `runbook.md` со ссылкой из `design.md`: запуск одной командой, контейнерные команды миграции, Ruff и pytest, переменные окружения и граница этапа 05. Проверка: команды выполняются в указанном порядке; отсутствие складского API этапа 06 отмечено явно.
- [x] 4.4 Выполнить итоговую сверку с действующими спецификациями и Zero-Defect, затем подготовить сводку Stop-and-Review. Проверка: зафиксированы фактические результаты `check_limits.py`, Ruff, pytest и OpenSpec validate; коммит ждёт отдельного подтверждения.
