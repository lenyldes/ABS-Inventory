# Дизайн основы приложения

## Context

Мотивация и границы — в [proposal.md](proposal.md), проверяемое поведение — в [спецификации основы](specs/app-foundation/spec.md). Согласованные правила предметной модели находятся в действующих спецификациях и [дизайне этапа 04](../archive/2026-09-28-domain-model-contracts/design.md). Сейчас в репозитории нет приложения и БД.

## Goals / Non-Goals

**Цели:** получить одну воспроизводимую схему для будущих этапов, отделить конфигурацию, HTTP, сервисы и хранение, проверить запуск и повторный старт на чистой БД.

**Вне целей:** проведение движений, расчёт остатков и прогноза, API справочников и закупок, проведение исправлений, синтетический демонстрационный набор этапа 09.

## Decisions

### 1. Слои и зависимости

Одно приложение FastAPI с пакетами конфигурации, API, моделей/доступа к данным и доменными модулями каталога, склада, прогнозирования и закупок. На этапе 05 доменные модули содержат только необходимые структуры; бизнес-правила появляются при реализации соответствующих этапов. Доступ к PostgreSQL — синхронный SQLAlchemy 2.x и psycopg, одна сессия на запрос или единицу фоновой работы. Это соответствует согласованному на этапе 04 модульному монолиту и делает границы транзакции явными. Асинхронный слой добавил бы второй режим исполнения без текущей потребности.

Docker Compose с первого шага служит средой разработки и сдачи. Зависимости устанавливаются через `pip` из `requirements.txt` в образ. Ruff и pytest запускаются командой Compose в контейнере с отдельной тестовой БД. Локальный `venv` и установка пакетов в системный Python не нужны. Требование ТЗ об управлении зависимостями выполняется через `requirements.txt`.

Согласованная базовая матрица версий на 28.09.2026:

| Компонент | Закреплённая версия |
|---|---|
| Образ приложения | `python:3.11.16-slim-bookworm` |
| Образ БД | `postgres:18.4` |
| HTTP | `fastapi==0.141.1`, `uvicorn==0.54.0` |
| БД и миграции | `SQLAlchemy==2.0.54`, `alembic==1.20.0`, `psycopg[binary]==3.3.6` |
| Валидация и конфигурация | `pydantic==2.13.5`, `pydantic-settings==2.15.0` |
| Проверки | `pytest==9.1.1`, `ruff==0.16.9`, `httpx==0.28.1` |

Все перечисленные Python-пакеты — прямые зависимости одного `requirements.txt` на этапе 05; версии транзитивных пакетов пока определит `pip`. SQLAlchemy остаётся на ветке 2.0: ветка 2.1 вышла непосредственно перед планированием изменения, а преимущества перехода для проекта не выявлены. При реализации необходимо проверить сборку обоих образов, совместную установку (`pip check`), миграцию и тесты в контейнере. Эта матрица пока не является результатом успешной сборки; несовместимость требует отдельного пересмотра зафиксированных версий.

### 2. Миграция полной модели

Первая ревизия Alembic создаёт таблицы `items`, `locations`, `suppliers`, `supplier_conditions`, `purchase_orders`, `batches`, `movements`, `movement_allocations`, `amendment_sets`, `amendment_entries`, `movement_versions` и `stock_locks`. Набор исправлений и его строки хранят предложенные действия и результат; версии сохраняют исходное и новое содержимое для аудита. Поля `created_at` и версия операции позволяют выстроить согласованный порядок и проверить устаревший просмотр. Детали предварительного просмотра реализуются на этапе 06 без новой предметной таблицы, если хватает этих записей и подписи состояния.

Внешние ключи связывают документ, партию, распределение, заказ и справочники; удаление связанных данных ограничено. SKU, код объекта и `supplier_id` уникальны. Номер документа уникален в пределах объекта среди активных движений посредством частичного уникального индекса; отменённое движение сохраняется в аудите и освобождает номер. Точность количеств — `NUMERIC(12,3)`, денег — `NUMERIC(12,2)`, даты операций хранятся отдельно от времени регистрации. Проверки SQL покрывают статические ограничения (`quantity`, диапазоны, неотрицательные значения); историческую обеспеченность и FEFO проверят сервисы этапа 06. Отдельного изменяемого поля остатка нет.

ORM-модели и миграция описывают одну схему; таблицы создаёт только Alembic. Изменение первоначальной ревизии после появления общих данных не допускается — следующие изменения идут новыми ревизиями.

### 3. Блокировка пары товара и объекта

`stock_locks` содержит уникальную пару внешних ключей на товар и объект. Сервис изменения остатков на этапе 06 сначала создаёт недостающую строку без дубликата, затем блокирует её `SELECT FOR UPDATE` внутри транзакции. Для нескольких пар используется стабильная сортировка ключей. Строка существует независимо от партий и доступного остатка; это сохраняет защиту и при пустом складе. Блокировка партий по отдельности не защищала бы отсутствие строк; advisory locks усложнили бы явную проверку области блокировки.

### 4. Запуск и начальные данные

На первом шаге Compose собирает минимальный образ приложения и поднимает PostgreSQL с проверкой готовности; данные PostgreSQL хранятся в именованном томе Docker вне репозитория. Обычный `docker compose down` сохраняет том, а `docker compose down -v` удаляет его вместе с данными. Последующие части добавляют в стартовую команду `alembic upgrade head`, идемпотентный скрипт сидов и HTTP. При ошибке подготовка прекращается с ненулевым кодом. `GET /health` проверяет БД коротким запросом и возвращает только статус. Конфигурация из переменных окружения валидируется при старте; `.env.example` содержит безопасные примеры, а действующий `.env` не включается в Git. Для проверок используется тот же образ с переопределённой командой и отдельной тестовой БД, чтобы обычные сиды не смешивались с тестовыми записями.

Сиды содержат небольшой стабильный набор товаров, объектов, поставщиков и закупочных условий. Повторный запуск использует уникальные деловые ключи и не удаляет дополнительные записи. Партии и движения появятся на этапе 06 через складской сервис, чтобы не обходить его правила.

### 5. Проверка

pytest проверяет конфигурацию, ограничения миграции и повторяемость сидов на изолированной PostgreSQL; HTTP-проверка подтверждает статусы `/health`. Запуск миграции на чистой БД и повторный старт через Compose проверяют путь пользователя. Ruff проверяет стиль. Набор пяти предметных тестов из ТЗ относится к этапам 06–07, когда появится расчётная логика.

## Risks / Trade-offs

- Полная схема создаётся раньше сервисной логики → проверять внешние ключи, уникальность и типы на чистой БД; не считать её наличие реализацией операций.
- Сиды из запуска могут конфликтовать с последующими пользовательскими правками → использовать стабильные ключи, вставлять отсутствующее и не перезаписывать существующее.
- Подготовка БД при каждом старте нескольких экземпляров может конкурировать → для прототипа один экземпляр сервиса; перед масштабированием вынести миграцию в отдельный одноразовый шаг.
- Именованный том сохраняет данные между запусками, но не заменяет резервную копию → процедуру копирования и восстановления серверного стенда определить на этапе 12.
- Схема аудита может потребовать уточнений при реализации исправлений → добавлять новые миграции, сохраняя уже записанную историю.

## Migration Plan

На пустой БД применить первую ревизию, загрузить справочники и проверить готовность. При повторном старте убедиться в отсутствии дубликатов. Откат до первых пользовательских данных возможен удалением тома прототипа; после появления данных используется обратная миграция только с явным учётом риска потери таблиц, а исправления схемы оформляются новой ревизией.

После реализации здесь фиксируются фактически проверенные команды запуска, миграций, Ruff и pytest в контейнере. Это короткая инструкция для этапа 05; полный README готовится на заключительном этапе ROADMAP.
