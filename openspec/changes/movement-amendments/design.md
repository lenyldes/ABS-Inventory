# Design

## Context

См. [proposal.md](proposal.md). Движения и распределения уже хранятся отдельно; остаток вычисляется из активной истории. Есть `stock_locks` для пары товар/объект, модели `amendment_sets`, `amendment_entries`, `movement_versions` и `current_version`, но рабочий API и автоматическая запись версий отсутствуют. Поступление по заказу изменяет `received_qty` и `pending_qty` в той же транзакции. Действующая спецификация запрещает молча перераспределять фактический расход.

## Goals / Non-Goals

**Goals:** один расчётный механизм для просмотра и подтверждения, проверка целого набора до записи, стабильные идентификаторы строк распределения и атомарность склада, аудита и приёмки заказа.

**Non-Goals:** редактирование SKU, создание новых строк расхода через исправление, изменение условий и количества заказа, воспроизведение прежних ответов прогноза до исправления, UI исправлений.

## Decisions

### 1. Хранение просмотра и защита от устаревания

Preview сохраняет исходный запрос, результат и подпись значимого состояния в `amendment_sets` и `amendment_entries`, затем освобождает транзакцию. Подпись строится из канонически сериализованных движений и строк распределения всех затронутых пар товар/объект, версий редактируемых движений, связанных партий и заказов. Она включает новые движения, даже если их `current_version` равна 1. Изменение `reason` при confirm недопустимо: он должен совпадать с сохранённым просмотром. Повторное подтверждение уже применённого просмотра отклоняется как конфликт.

Preview определяет старые и предложенные пары, берёт их блокировки в порядке `(item_id, location_id)`, затем перечитывает данные и сохраняет снимок. Confirm в том же порядке блокирует пары, затем связанные заказы в порядке ID, перечитывает данные и сравнивает подпись и `expected_version`. При несовпадении возвращает `409 stale_preview`; при появившейся блокирующей зависимости — `422 dependency_violation`. Сравнение выполняется до записи; после него набор, аудит и поставки фиксируются одной транзакцией. Такой подход продолжает существующую схему блокировки. Хранить открытую транзакцию между HTTP-запросами невозможно; проверять только версии редактируемых строк недостаточно для нового зависимого расхода.

### 2. Симуляция набора на неизменяемых снимках

Сервис загружает движения, партии и распределения затронутых пар, создаёт проектируемую копию и применяет все предложенные изменения к ней без промежуточной записи в БД. Валидация проходит по итоговому набору: тип и знак количества, дата, принадлежность партии и объекта, годность на дату расхода, сумма строк, возвраты и их даты, документы, исторический остаток после каждой операции. Для `receipt` проверяются и синхронно меняются атрибуты партии (`receipt_date`, `receipt_doc_number`, `location_id`) там, где изменяется соответствующее поле движения. Перемещение прихода отклоняется при любой зависимой операции с партией на старом объекте, включая расход, возврат, списание и корректировку; это сохраняет связи партий.

Результат preview содержит разницу текущего и доступного остатков по затронутым партиям, идентификаторы затронутых операций и конкретные блокеры. Для известных нарушений зависимости preview возвращает `can_apply: false`; структурно недопустимый запрос получает `400`/`404`/`422` по контракту. Confirm выполняет ту же симуляцию под блокировками. Используется существующая чистая расчётная логика после её расширения, а не отдельные правила для API. Проверять операции по очереди в БД нельзя: допустимый набор может иметь временно отрицательный остаток после первой правки.

### 3. Фактические строки расхода и возвраты

При изменении количества `consume` клиент указывает `allocation_quantities` для всех изменяемых строк; остальные остаются прежними. Строки сохраняют свои ID и партии. Положительность, сумма и достаточность каждой партии проверяются на проектируемой истории. Отдельное поле `allocation_id` + `batch_id` меняет только названную строку, с объяснением отклонения от FEFO; цена распределения следует цене выбранной партии. Связанные возвраты при допустимом переносе партии должны отражать новую партию и цену той же строки, иначе остаток станет несогласованным; это показывается как затронутая операция и сохраняется в её аудите. Если возврат отменён или его количество изменено в том же наборе, лимит проверяется по итоговому состоянию. Отмена исходного расхода требует явной отмены всех активных возвратов по нему.

Альтернатива — автоматически распределять новую разницу по FEFO — противоречит сохранению фактической выдачи. Создание/удаление строк в этом этапе не поддерживается, чтобы не менять идентификаторы, на которые ссылаются возвраты.

### 4. Приёмка заказа и аудит

Для каждого затронутого заказа итоговое `received_qty` вычисляется из всех его активных `receipt`, `pending_qty = expected_qty - received_qty`; отрицательное значение блокирует весь набор. Статус выводится из итоговых количеств с учётом уже задержанного заказа: полная приёмка даёт `received`, частичная — `partially_received` либо `delayed` при просроченной ожидаемой дате. Отмена приёмки восстанавливает непринятое количество. Правки без заказа не меняют заказ. Пересчёт из активных поступлений уменьшает риск дрейфа счётчиков по сравнению с последовательным применением дельт.

Версия 1 записывается при создании движения после формирования распределений, до фиксации транзакции. Каждая успешная правка или отмена добавляет полную JSON-копию состояния и причину, увеличивая `current_version`; ответ истории вычисляет `changes` из соседних снимков. Если из-за переноса партии возврат меняется автоматически, для него также добавляется версия с той же причиной и ссылкой на набор. Для ранее созданных движений новая миграция создаёт версию 1 из текущего состояния и исходного `created_at`; более раннюю неизвестную историю не реконструирует. Перезаписывать старый снимок при правке запрещено.

## Risks / Trade-offs

- Полная история пары в подписи и симуляции дорожает при росте журнала → сначала ограничить загрузку затронутыми парами и измерить, затем оптимизировать без изменения контракта.
- Новый расход между preview и confirm делает просмотр устаревшим даже без фактического конфликта → это сознательная цена точного подтверждения показанного результата.
- Различие между датой исправления и исходной датой операции может сбить аудит → `created_at` версии означает время правки, `operation_date` остаётся отдельным полем снимка.
- Старые записи не имеют исходного аудита → миграция отмечает только найденное состояние, без вымышленной предыстории.

## Migration Plan

Добавить следующую ревизию Alembic для заполнения отсутствующих версий 1 и нужных ограничений/полей аудита, не изменяя начальную миграцию. Развёртывать новую версию приложения после миграции; сиды и обычный API с этого момента создают начальную версию через общий сервис записи. Откат приложения не должен удалять движения и версии; при возврате к старой версии API исправлений отключается до повторного обновления, данные сохраняются.
