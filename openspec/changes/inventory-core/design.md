# Design

## Context

Мотивация и объём описаны в [proposal.md](proposal.md). В этапе 05 уже созданы модели `Batch`, `Movement`, `MovementAllocation`, `StockLock`, заказов поставщику и первая миграция. Сейчас приложение отдаёт только `/` и `/health`; сиды содержат справочники без складских записей. Правила операций и HTTP-контракт заданы действующими спецификациями `inventory`, `catalog`, `procurement` и архивным дизайном `domain-model-contracts`.

## Goals / Non-Goals

**Goals:** реализовать учёт без отдельно изменяемого остатка; проводить каждую операцию атомарно; обеспечить повторяемые чтения на дату и воспроизводимые проверки реальной PostgreSQL.

**Non-Goals:** исправления и отмена движений с preview/confirm, расчёты среднего расхода и прогноза, создание заказов поставщику через API, большой демонстрационный набор этапа 09.

## Decisions

### 1. Границы слоёв и расчёт остатка

Маршруты FastAPI принимают и сериализуют данные, сервисы `app/inventory/` управляют операциями, а репозиторий выполняет запросы SQLAlchemy. Чистые функции домена вычисляют порядок FEFO, вклад движения в партию и проверку исторической обеспеченности из подготовленных записей. Учётный остаток партии складывается из активного прихода, возвратов и положительных корректировок за вычетом распределённых расходов, списаний и отрицательных корректировок. Дата `as_of` ограничивает движения по `operation_date`; доступное количество дополнительно исключает партии с `expiry_date < as_of`.

Сохраняем распределения фактических расходов. Повторный расчёт на прошлую дату не перераспределяет их после позднего прихода. Для одинаковой даты используем согласованный бизнес-порядок и стабильные `created_at`, `id`. Материализованный остаток ускорил бы чтение, но создал бы второе изменяемое состояние и усложнил бы исправления.

### 2. Запись, ретроспектива и блокировка

В одной транзакции сервис определяет пару `(item_id, location_id)`, создаёт при необходимости строку `stock_locks` через защищённую вставку и берёт `SELECT FOR UPDATE`. Под этой блокировкой читает историю, проверяет правила операции, сохраняет движение и распределения, пересчитывает историю от даты операции до текущего дня, затем завершает транзакцию. Уникальный индекс активного документа остаётся последней защитой от гонки номеров; его нарушение преобразуется в `409`. При ошибке всё откатывается.

Для расхода FEFO выбирает доступные на дату операции партии в согласованном порядке. `writeoff` и `correction` работают с указанной партией; возврат связан с конкретной строкой исходного расхода и сохраняет её цену. Просроченный возврат увеличивает учётный, но не доступный остаток. Проверка истории рассматривает и отрицательный остаток отдельной партии, и связанные возвраты. Поздний приход не меняет уже записанные распределения; журнал вычисляет предупреждение `fefo_deviation` сравнением сохранённых строк с порядком FEFO по актуальной истории на дату расхода.

При `receipt` с `purchase_order_id` тот же сервис под блокировкой заказа проверяет товар, объект, поставщика и неполученное количество, затем атомарно обновляет `received_qty`, `pending_qty` и статус. Полный API управления заказами относится к этапу 08; в этом изменении связь проверяется на подготовленных заказах.

### 3. Контракты API и этапность показателей

`POST /api/movements`, `GET /api/movements`, `GET /api/stock` и `GET /api/stock/{sku}` следуют действующей спецификации `inventory` и дельте этого изменения. Pydantic проверяет формат и сочетания полей по типам; сервис проверяет существование ссылок и динамические инварианты. Ошибки возвращают согласованный машинный код, русское сообщение и детали. Для списка движений `total` вычисляется до `limit`/`offset`, сортировка при равных датах стабилизируется `id`. У записей расхода журнал возвращает `warnings: []` либо объект с `code: fefo_deviation`, русским сообщением и ID партий.

Сводка этапа 06 возвращает рассчитанные остатки и ближайшую годность. Поля `average_daily_consumption` и `days_of_stock` пока имеют допустимое контрактом значение `null`; их отдельный детерминированный расчёт добавляется на этапе 07. Складские операции и детализация партий доступны сейчас, даже если прогноз ещё отсутствует.

### 4. Стартовые данные и проверки

Существующий загрузчик после справочников создаёт небольшой набор поступлений и расхода с постоянными служебными номерами документов. Он проходит через те же правила учёта, что и API, проверяет наличие документа перед вставкой и не обновляет существующие записи. Даты и срок годности задаются относительно даты подготовки в `Europe/Moscow`, чтобы новый стенд сразу содержал доступную партию; повторный запуск не передатирует уже созданное. Расширенные пограничные сценарии остаются этапу 09.

Тесты чистой логики покрывают FEFO, точность Decimal и исторический расчёт. Интеграционные тесты на изолированной PostgreSQL проверяют транзакции, конкурирующие расходы, возвраты и документы; HTTP-тесты проверяют контракты, фильтры, пагинацию и статусы. Обязательные проверки добавляются в `scripts/check.sh` и запускаются общей командой перед ревью.

## Risks / Trade-offs

- Пересчёт истории при ретроспективной записи становится дороже с ростом журнала → ограничить запросы затронутой парой и датой; оптимизацию выполнять после измерения.
- Поздний приход может выявить отклонение старой выдачи от FEFO → сохранять фактическое распределение и показывать отклонение; исправление партии проводить только в следующем изменении.
- Относительные даты сидов делают первое состояние зависящим от дня запуска → фиксировать дату при первой загрузке и проверять повторный запуск без перезаписи.
- Складской API появляется раньше расчётных показателей этапа 07 → возвращать для них `null`, сохраняя согласованную форму ответа.

## Migration Plan

Использовать существующую схему; при необходимости новых ограничений добавить следующую ревизию Alembic, не изменяя первоначальную. При запуске после миграции загрузить только отсутствующие стартовые документы. Откат к предыдущей версии приложения не должен удалять созданные движения; при необходимости исключить новые сиды из загрузчика, сохранив данные для последующего возобновления.
