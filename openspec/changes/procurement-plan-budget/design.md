# Design

## Context

См. `proposal.md` и `specs/procurement-plan-budget/spec.md`. Сейчас `POST /api/forecast` рассчитывает одну позицию до конца горизонта. `app/forecasting` уже содержит расчёт среднего расхода, FEFO-моделирование, выбор цены и округление заказа; закупочные условия и ожидаемые заказы читаются из БД. Каталог хранит категорию товара и объект. API управления закупочными условиями и заказами пока не подключён; план читает существующие записи и не зависит от нового CRUD.

## Goals / Non-Goals

**Goals:**

- Один детерминированный расчётный снимок на запрос: все позиции и все бюджетные итоги выводятся из него.
- Чистое ядро планирования с отдельной проверкой арифметики и дневного поведения без HTTP.
- Сохранение правил действующего прогноза для расхода, FEFO, условий поставщика и цены.

**Non-Goals:**

- Не изменять семантику одиночной рекомендации `/api/forecast` и не приравнивать её объём к сумме повторных заказов.
- Не сохранять расчёт, не создавать заказов, не оптимизировать выбор поставщика и не менять закупки под бюджетный лимит.

## Decisions

### 1. Отдельный API и слой расчёта

Добавить `POST /api/procurement/plan` с отдельными схемами запроса/ответа и сервисом, который загружает выбранные пары из каталога и вызывает чистое ядро для каждой пары. Параметры и ошибки описаны в спецификации. Все пары считываются в одной транзакции с согласованным снимком PostgreSQL (`REPEATABLE READ`), чтобы параллельные движения не дали разным позициям разные состояния; запрос ничего не записывает. Порядок результата устойчивый: объект, категория, SKU, дата заказа, порядковый номер позиции. Альтернатива — многократно вызывать HTTP `/api/forecast`; она повторяет загрузки и даёт одну рекомендацию на горизонт вместо последовательного плана.

### 2. Дневное планирование и месячная цель пополнения

Для пары зафиксировать `as_of`, средний дневной расход за 90 дней, начальные FEFO-партии, действующие ожидаемые поставки, цену и условия основного поставщика. Сначала моделировать дни без новых заказов и найти первый день падения ниже страхового запаса; при нулевых страховых днях — день исчерпания. Намеченная дата заказа — этот день минус срок поставки, но не раньше `as_of`; дата прихода — дата заказа плюс срок поставки. Если она за горизонтом, записать риск без бесполезной позиции.

Для положительной потребности подобрать минимальное количество до округления, которое после прихода покрывает расход без нового дефицита до `min(дата прихода + 1 календарный месяц, конец горизонта)` и оставляет целевой страховой запас на конце этого интервала. Подбор опирается на ту же дневную FEFO-модель с уже оформленными и ранее спланированными поступлениями; после него применяются минимум и кратность упаковки. Добавить виртуальное поступление в снимок, вновь моделировать оставшиеся дни и искать следующий порог. Пока виртуальная поставка ещё в пути, не создавать дубликат для тех же необеспеченных дней: отмечать дефицит до её прихода. Ограничить число итераций числом прогнозных дней и завершать цикл только при продвижении даты порога или отсутствии потребности. Альтернатива — разделить единый квартальный заказ на три равные части; это нарушает FEFO, минимум заказа и календарь реальных поставок.

Виртуальные партии, как и будущие ожидаемые поставки действующего прогноза, считаются годными до конца горизонта. Реальные складские движения не создаются. Для пары без срока поставки использовать одну недатированную оценку всего горизонта по формуле одиночной рекомендации; она не участвует в моделировании будущего остатка. Нулевая история расхода не порождает заказ.

### 3. Общие правила без изменения одиночного прогноза

Выделить переиспользуемые чистые операции округления количества и денежной стоимости из существующего расчёта либо вызвать их из общего модуля. Новое ядро использует существующие функции расхода и FEFO; исходный `/api/forecast` сохраняет контракт и контрольные результаты. Совпадают исходный снимок, цена, предупреждения о неполной истории, правила поставок и округления. Сумма нескольких месячных заказов может отличаться от одной рекомендации на весь горизонт, так как минимум и упаковка применяются к каждой позиции отдельно.

### 4. Бюджет как проекция позиций

После расчёта всех пар сформировать неизменяемый список новых позиций. По нему одной функцией построить независимые разрезы: месяц заказа, SKU, категория и объект. Для каждой группы сложить только известные `total_cost` типа `Decimal` без промежуточного округления. Недатированные позиции идут в особую группу; позиции без цены увеличивают счётчик неизвестных сумм. Общий известный итог равен сумме календарных групп и группы без даты; сумма каждого из остальных разрезов равна общему итогу. Не складывать разрезы между собой — это альтернативные представления одних позиций.

Цена берётся один раз на `as_of` по действующему правилу; смена цены в течение горизонта не моделируется. Лимит сравнивается с общим известным итогом. При неизвестной цене превышение лимита можно доказать по известной части, а соблюдение — нельзя; поэтому статус `within` допустим только при полной оценке. Неизвестная дата отдельно отмечает неполное распределение по месяцам. У уже оформленных заказов может не быть достоверной даты размещения; их стоимость не смешивается с бюджетом новых решений.

### 5. Границы периода и объяснение

План использует то же сложение месяцев, что `/api/forecast`; «3 месяца» означает скользящий горизонт, не календарный квартал. Бюджетные месяцы берутся из даты заказа, начиная с `as_of`; ответ явно показывает частичные первый и последний месяцы. Для каждой позиции вернуть параметры расхода, остатка, ожидаемых поставок, условия заказа, источник цены, потребность до округления и предупреждения. Общий ответ объясняет разницу между оценочной стоимостью и фактическим расходом денежных средств.

## Risks / Trade-offs

- Постоянный средний расход на 12 месяцев может плохо отражать сезонность → показывать срок горизонта, основание из 90 дней и предупреждение о допущении; сезонность остаётся отдельной задачей.
- Пошаговое FEFO-моделирование по многим парам и дням может быть дорогим → грузить данные пакетами и переиспользовать снимки; измерить время на демонстрационном наборе без преждевременного усложнения алгоритма.
- Позиции без цены или срока могут дать ложное ощущение полного бюджета → отдельные флаги полноты, счётчики и группа без даты, а не нулевые подстановки.
- Месячное округление заказов может увеличить итог по сравнению с одиночным прогнозом → объяснять стратегию пополнения и сверять сумму только с позициями нового плана.

## Migration Plan

Миграция БД не требуется. Новый маршрут добавляется без изменения существующих. Откат — убрать маршрут и модуль планирования; сохранённых планов и новых данных нет.
