# Design: Итоговая передача проекта и структура README

## Context

Проект ABS Inventory & Procurement Assistant прошёл все стадии реализации (этапы 01–12 дорожной карты). Готовы ядро складского учёта, расчётные модули прогнозирования, план закупок и бюджет, веб-интерфейс, синтетические демоданные и развёрнут боевой стенд на `https://abs-inventory.lenyldes.ru`. Согласно `AGENTS.md`, размер создаваемого `README.md` не должен превышать 10 000 символов UTF-8. Документ должен быть предельно концентрированным, технически точным и убедительным.

## Goals / Non-Goals

**Goals:**
- Сформировать законченный, ёмкий и презентабельный файл `README.md`, полностью закрывающий требования ТЗ и правила проекта.
- Наглядно продемонстрировать инженерный подход: разработку в паре с ИИ (OpenSpec, TDD, Zero-Defect), модульную архитектуру и чистые расчёты.
- Дать мгновенный доступ к демонстрации: ссылка на живой стенд с интерактивным проверочным интерфейсом, Swagger UI и воспроизводимым сбросом данных.
- Подробно описать алгоритм расчёта остатка без денормализации и распределение ответственности между слоями.
- Зафиксировать ответы автора на вопросы тестового задания о мотивации, роли и графике.
- Актуализировать статус этапа 13 в `doc/ROADMAP.md`.

**Non-Goals:**
- Изменение существующего кода бизнес-логики, схемы БД или API-эндпоинтов.
- Раздувание документации за пределы лимита 10 000 символов (декомпозиция и ёмкость формулировок вместо многостраничных трактатов).

## Decisions

### 1. Архитектурная декомпозиция и балансировка объема README
- *Решение*: Организовать `README.md` в виде 10 компактных логических секций с использованием таблиц и списков.
- *Обоснование*: Обеспечивает мгновенную навигацию для технического лида или рекрутера при беглом просмотре и укладывается в бюджет символов (~6 000–8 000 символов из допустимых 10 000).

### 2. Формула и принцип расчёта остатка
- *Решение*: В явном виде зафиксировать в секции архитектуры:
  $$\text{Stock}(sku, loc, as\_of) = \sum \text{Receipts} + \sum \text{Returns} \pm \sum \text{Corrections} - \sum \text{Consumptions} - \sum \text{Writeoffs}$$
  по активным партиям с датой поступления $\le as\_of$. Просроченные партии ($\text{expiry\_date} < as\_of$) не участвуют в доступном остатке и требуют явного акта списания.
- *Обоснование*: Прямое требование ТЗ — остаток вычисляется динамически из движений и партий, а не хранится отдельным изменяемым полем.

### 3. Разделение ответственности слоёв
- *Решение*: Описать трёхзвенную структуру:
  - *API & DTO* (`app/api`): валидация через Pydantic v2, маппинг ошибок в статусы 400, 404, 409, 422.
  - *Persistence & Lock* (`app/inventory/repository.py`, `app/models`): SQLAlchemy 2.0, блокировки `stock_locks` для предотвращения race condition при списании.
  - *Pure Domain Calculations* (`app/inventory/calculator.py`, `app/forecasting/`, `app/procurement_plan/`): детерминированные чистые функции без внешних зависимостей.

### 4. Презентация стенда с интерактивным тестированием
- *Решение*: Вынести блок Live Demo в начало документа с акцентом на то, что на `https://abs-inventory.lenyldes.ru` доступен специальный экран «01 · Проверка API», где любые эндпоинты ТЗ проверяются в браузере «из коробки» без Postman/curl.

### 5. Аутентичный блок мотивации автора
- *Решение*: Включить прямые ответы автора на 3 вопроса из ТЗ: польза реального продукта, опыт коммерческого API с LLM, роль backend-разработчика широкого профиля и готовность к полной занятости (~40 ч/нед на 2–3 мес.).

## Risks / Trade-offs

- **[Риск]**: Превышение лимита в 10 000 символов при подробном описании всех разделов.  
  *Митигация*: Контроль размера через `scripts/check.sh`, отказ от длинных листингов кода в пользу концентрированных таблиц и архитектурных схем.
- **[Риск]**: Рассинхронизация параметров `.env.example` с документацией.  
  *Митигация*: Точная сверка описания каждого параметра с актуальным файлом `.env.example`.
