# Подход к оформлению дорожной карты

## Context

Мотивация и границы изменения описаны в `proposal.md`. В проекте пока нет кода и действующих спецификаций. Доступны описание вакансии и два PDF в `doc/SOW`: тестовое backend-задание и более широкие бизнес-требования продукта.

Этот дизайн нужен для устранения неоднозначности между обязательными требованиями, согласованным расширением и архитектурными предложениями. Он определяет способ документирования; архитектуру будущего приложения предстоит уточнять отдельными изменениями.

## Goals / Non-Goals

**Цели:** сделать дорожную карту пригодной для выбора следующего небольшого изменения, проверки результата каждого этапа и отслеживания открытых решений.

**Вне целей:** подробная декомпозиция реализации, утверждение всех бизнес-требований в качестве обязательств, выбор frontend или провайдера модели, создание иных проектных документов.

## Decisions

### 1. Один документ и явные статусы решений

`doc/ROADMAP.md` содержит: цель и источники; границы объёма; архитектурные ориентиры со статусами; этапы; открытые вопросы; порядок дальнейшей декомпозиции. Используется русский язык, кроме имён технологий, файлов и API.

Вместо нескольких документов на первом шаге выбирается единая карта: её проще обсуждать и актуализировать. Вместо полного копирования PDF используются относительные ссылки на оба PDF и описание вакансии; перенос исходников в Markdown остаётся отдельным этапом.

Различаются три статуса:
- **Требование задания:** Python 3.11, FastAPI, PostgreSQL, SQLAlchemy, Pydantic, Alembic; остаток из движений и партий; FEFO; отдельная детерминированная расчётная логика; pytest; запуск через Docker Compose.
- **Согласовано с пользователем:** качество важнее ограничения в три дня; небольшие изменения OpenSpec; русский язык; опубликованный прототип; полный целевой сценарий; интерфейс и AI-чат; API модели предоставит пользователь.
- **Предложено для обсуждения:** модульный монолит; границы модулей API, бизнес-логики и доступа к данным; обращение модели к разрешённым инструментам backend; механизм защиты от конкурентных списаний.

Обязательная детерминированность числовых расчётов отделяется от ещё не выбранного механизма вызова инструментов модели. Новые библиотеки и версии сверх требований задания не назначаются.

### 2. Три границы объёма

Обязательный backend перечисляется компактно: POST/GET `/api/movements`, GET `/api/stock`, GET `/api/stock/{sku}`, POST `/api/forecast`, GET `/api/alerts`; FEFO и проверки; тесты; миграции, стартовые данные, Docker Compose, README и `.env.example`.

Согласованное расширение: план закупок по нескольким товарам и сводный бюджет, интерфейс, AI-чат, демонстрационные сценарии, серверный стенд и отчёт. Поддерживаемые периоды, разрезы и критерии приёмки расширения уточняются до соответствующей реализации.

Остальные возможности бизнес-требований не считаются автоматически принятыми: например, анализ маржинальности услуг и сезонности требуют отдельного решения. Автоматическое размещение заказов и оплата, полноценная ERP/WMS и промышленная ролевая модель остаются вне целевого прототипа.

Альтернатива — принять весь документ БТ сразу — размывает критерии готовности текущего проекта.

### 3. Этапы с проверяемым результатом

Для каждого этапа указываются идентификатор, цель/результат, зависимости, критерий завершения и статус. Начальные статусы честно отражают состояние: наличие плана не означает готовность функций. Календарные оценки не назначаются.

| ID | Этап | Зависимости | Основа критерия завершения |
|---|---|---|---|
| 01 | Дорожная карта и архитектурные ориентиры | Нет | Создана и проверена карта; предложения отделены от решений |
| 02 | Правила работы в AGENTS.md | 01 | Описаны язык, размер итераций, OpenSpec и проверки |
| 03 | Требования в Markdown и проверка правил работы | 02 | Оба PDF перенесены и сверены, неоднозначности вынесены отдельно; правила AGENTS.md проверены на практике, необходимые уточнения обсуждены и внесены |
| 04 | Предметная модель и контракты | 02, 03 | Описаны сущности, связи, семантика операций и API; блокирующие вопросы учёта разрешены |
| 05 | Основа приложения | 04 | Приложение и PostgreSQL запускаются, миграции и автоматические проверки работают |
| 06 | Складской учёт | 05 | Движения, остатки, FEFO и ошибки проверены, включая конкурентные списания |
| 07 | Прогноз и риски | 06 | Формулы и предупреждения проверены, результаты содержат исходные данные и объяснение |
| 08 | План закупок и бюджет | 07 | Потребности агрегируются, суммы согласованы с расчётами по позициям |
| 09 | Демонстрационные данные | 06–08 | Подготовлен воспроизводимый набор с проверенными ожидаемыми результатами |
| 10 | Пользовательский интерфейс | 08, 09 | Пользователь проходит целевой сценарий и меняет параметры расчёта |
| 11 | AI-помощник | 08–10, доступ к API модели | Диалоги на русском используют реальные расчёты; проверены уточнения, отсутствие данных и сбои API |
| 12 | Приёмка и развёртывание | 10, 11 | Требования проверены, стенд доступен по ссылке, проверены доступ, журналирование и восстановление демоданных |
| 13 | Передача и защита | 12 | Есть README, отчёт, результаты проверок, ограничения и сценарий демонстрации |

Это логический порядок, а не запрет на независимую работу. Минимальные фикстуры и стартовые данные создаются уже на этапах 05–07; этап 09 расширяет их для демонстрации. Тесты и документация сопровождают каждый этап, подготовка отчёта идёт по мере получения результатов. Для AI и сквозного сценария планируется набор не менее 20 контрольных вопросов/сценариев из БТ с явными ожидаемыми результатами.

### 4. Декомпозиция через OpenSpec

Один этап может потребовать нескольких небольших изменений. Перед каждым изменением уточняются границы и критерии приёмки; затем оформляются артефакты, выполняется реализация и проверка. Подробные задачи живут в соответствующем изменении, а ROADMAP остаётся обзорным документом.

Альтернатива — заранее расписать все технические задачи — создаёт ложную определённость до согласования правил учёта.

## Risks / Trade-offs

- Смешение тестового и полного продукта → отдельные границы обязательного объёма, согласованного расширения и отложенных возможностей.
- Архитектурная рекомендация воспринимается как утверждённая → явные статусы и ссылки на будущий этап решения.
- Слишком крупные этапы мешают коротким итерациям → возможность нескольких OpenSpec-изменений на этап.
- Демоданные стареют относительно текущей даты → запланировать воспроизводимую дату расчёта и стратегию обновления данных; конкретное решение принять при проектировании.
- Формальная проверка Markdown не доказывает полноту плана → вручную сверить карту с источниками и согласованным объёмом.

## Open Questions

Эти вопросы не блокируют создание ROADMAP, но должны быть решены до зависимой реализации:
- Этап 04: семантика `return`/`correction`, операции задним числом, уникальность номера документа, расход из нескольких партий и конкурентный доступ.
- Этапы 04, 07: календарные границы периодов, учёт просроченных остатков и ожидаемых поставок, воспроизводимость даты расчёта, расхождения числового примера с формулами.
- Этап 08: разрезы плана и бюджета, периоды, допустимые изменения параметров.
- Этап 10: стек интерфейса и состав экранов.
- Этап 11: контракт API модели, поддержка инструментов, ограничения и обработка ошибок.
- Этап 12: окружение сервера, домен, HTTPS и способ доступа к демонстрации.

Создание документа не требует миграций или развёртывания. Откат ограничивается удалением добавленного `doc/ROADMAP.md`.
