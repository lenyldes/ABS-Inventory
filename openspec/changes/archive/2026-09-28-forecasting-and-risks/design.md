# Design

## Context

См. [proposal.md](proposal.md). Склад уже хранит партии, активные движения, распределения расхода, связи возвратов и исправления. `calculate_stock_balance` получает доменные снимки и вычисляет остаток на дату; `/api/stock` пока возвращает `null` для среднего расхода и дней запаса. Есть модели `SupplierCondition` и `PurchaseOrder`, но API управления ими относится к этапу 08. Действующие спецификации `forecasting`, `alerts`, `procurement` и `inventory` задают формулы и публичные контракты.

## Goals / Non-Goals

**Goals:** одни и те же исходные данные и чистые расчёты для прогноза, предупреждений и сводки склада; детерминированный ответ на `as_of`; отсутствие побочных эффектов при чтении.

**Non-Goals:** создание закупочных заказов, изменение закупочных условий через API, сохранение снимков прежних прогнозов, сезонная модель и автоматическое списание просрочки.

## Decisions

### 1. Подготовка данных отдельно от вычислений

Репозиторий загружает для пары товар/объект текущую исправленную историю, партии, неполученные заказы и основного поставщика. Поступления выбранного поставщика с датой не позже `as_of` служат источником последней цены; при их отсутствии используется ориентировочная цена условия. Преобразованные снимки передаются в чистые функции `app/forecasting/`. FastAPI отвечает за разбор параметров, коды ошибок и сериализацию. Повторное использование существующих снимков склада снижает риск двух разных трактовок FEFO и исправлений; расчёт внутри маршрута усложнил бы независимые проверки.

Поставка с `expected_date <= as_of` и неполученным остатком считается задержанной при чтении независимо от сохранённого статуса, поэтому устаревший статус не делает её доступной. Поставки с датой позже `as_of` учитываются по своей дате, а уже принятые количества остаются только в партиях. Прогноз ничего не сохраняет и не меняет статус заказа.

### 2. Точность, история и дневная модель

Чистый расчёт расхода суммирует `consume` за 90 календарных дней и вычитает активные связанные `return`, известные на `as_of`, по дате исходного расхода. `writeoff` и `correction` исключены. Знаменатель остаётся 90 даже при короткой истории. Отсутствие положительного чистого расхода порождает нулевой средний расход и ограничения расчёта по спецификации. Внутренние вычисления используют `Decimal` не менее чем с шестью знаками; количества и стоимость округляются только при формировании ответа и заказа, чтобы ежедневное округление не накапливало ошибку.

На каждый день прогноз сначала исключает просроченные партии, затем добавляет поставки этого дня, затем распределяет средний расход по FEFO и фиксирует непокрытую часть. Расчёт сохраняет дневные значения для `daily_forecast`, даты дефицита и риск списания. Рекомендуемая закупка определяется суммарной потребностью и целевым запасом с учётом действительно пригодного количества; временный дефицит до прихода поставки показывается отдельно. Новый заказ не добавляется в модель текущего покрытия: это рекомендация, а не подтверждённая поставка.

### 3. Переиспользование расчётов и контракты

`/api/stock` получает средний расход и дни запаса из того же набора чистых функций, который используется `/api/forecast`. `/api/alerts` строится из общего расчётного снимка и прогноза, а затем применяет тип, уровень, фильтры, устойчивый порядок и пагинацию. Без явного `horizon_days` срок прогнозирования вычисляется отдельно для каждого товара как `max(30, L + 1)`, при неизвестном `L` — 30; явный горизонт одинаков для всех. Применённый горизонт и конец периода входят в показатели прогнозных предупреждений. Отдельный алгоритм предупреждений с собственными формулами создал бы расхождения между эндпоинтами.

`explanation` собирается из фактически использованных величин, формул и допущений в отдельную структурированную схему. Текст каждого элемента остаётся понятным человеку, а значения и источники данных доступны для проверки. Поля, невозможные без цены или срока поставки, остаются `null` с предупреждением.

### 4. Проверки и этапность

Сначала отдельно проверяются чистые формулы, календарь, точность, возвраты и дневное FEFO. Затем на PostgreSQL проверяются выбор актуальной исправленной истории, источник цены, задержанные и частично принятые поставки. После этого проверяются три HTTP-контракта и согласованность их показателей на одной дате. Управление закупочными условиями и заказами через API остаётся отдельным этапом 08; интеграционные сценарии этапа 07 готовят такие записи напрямую в фикстурах.

## Risks / Trade-offs

- Длинный горизонт и список многих товаров увеличивают число дневных шагов → фильтровать пары до расчёта, загружать данные без повторных запросов на каждый день и измерять узкие места на интеграционных сценариях.
- Поздние исправления меняют ответы на прошлую дату → рассчитывать по актуальной исправленной истории и не обещать воспроизведение прежнего ответа.
- Будущие поставки без известного срока годности считаются пригодными на горизонте → явно указывать это допущение в объяснении.
- Отсутствие срока поставки или цены уменьшает точность рекомендации → возвращать зависимые поля как `null` и объяснять ограничение.

## Migration Plan

Новые таблицы и изменение данных не требуются. После обновления приложения расчётные поля `/api/stock` заполняются, а новые маршруты становятся доступны; обратный переход к прежней версии не меняет складские записи. До слияния изменение проходит обязательную общую проверку и отдельное ревью.
