# Design

## Context

См. `proposal.md` и `specs/demo-data/spec.md`. Сейчас `python -m app.seeds` при старте Compose идемпотентно добавляет справочники и три движения относительно текущей даты. Загрузчик не перезаписывает найденные деловые ключи. Это безопасно для обычного запуска, но не позволяет перенести весь сценарий на другую `as_of`.

Движения должны создаваться через действующие складские операции: так партии, FEFO-распределения и версии остаются согласованными. Ожидаемые заказы пока создаются напрямую ORM, так как CRUD из спецификации `procurement` ещё не подключён. Первичные ID БД нестабильны при пересборке, поэтому контрольные ответы не могут опираться на них.

Для реализации достаточно точечно свериться с `app/seeds/loader.py`, `app/inventory/receipt_consume.py`, `app/models/catalog.py`, `app/models/inventory.py`, `app/models/procurement.py`, `app/models/amendments.py`, `app/forecasting/procurement_repository.py`, `app/api/stock_schemas.py`, `app/api/forecast_schemas.py`, `app/api/alerts_schemas.py`, `app/api/plan_schemas.py` и тестовой фикстурой `tests/conftest.py`. Контракты зафиксированы в `openspec/specs/`; перечитывать архив изменений не требуется.

## Goals / Non-Goals

**Goals:**

- Одним явным CLI-запуском готовить полный демонабор в одной транзакции.
- Дать UI, AI-помощнику и стенду стабильные SKU, объекты и сценарии.
- Проверять эталонные числа независимо от production-расчётов.
- Сохранить безопасную семантику текущих стартовых сидов.

**Non-Goals:**

- Не моделировать сезонность, плановую загрузку SPA и маржинальность.
- Не добавлять HTTP API управления демоданными и не запускать пересборку автоматически при каждом старте.
- Не изменять схему БД или контракты действующих API.
- Не создавать из демонабора общий генератор произвольных тестовых данных.

## Decisions

### 1. Отдельный CLI и пространство деловых ключей

Добавить пакет `app/demo_data` и команду:

```bash
python -m app.demo_data --as-of YYYY-MM-DD [--replace]
```

Команда без `--replace` создаёт отсутствующий набор, повтор на ту же дату считает успешным no-op, а при другой дате отказывает. `--replace` явно разрешает транзакционную замену на другую дату. Это отделяет потенциально разрушающую операцию от `python -m app.seeds`, которая остаётся в старте Compose без изменений.

Все демоключи получают стабильный префикс `DEMO-`: SKU, коды объектов, поставщиков, номера документов и партий. Контрольная дата выводится из даты стабильного опорного движения с известным смещением. Отдельная таблица метаданных не нужна.

Опорное движение — приход `DEMO-REC-OIL-BASE` для `DEMO-OIL` на `as_of - 100 дней`. При повторе найденная дата прихода + 100 дней определяет исходную `as_of`. Сверить существующие ключи `DEMO-` с полным перечнем в определениях: при отсутствующем опорном движении, недостающем или лишнем ключе отказать как при неполном или конфликтующем наборе. Не присваивать себе чужие записи с тем же префиксом. Повтор на ту же дату не добавляет и не обновляет строк. `--replace` проходит проверку внешних ссылок и пересоздаёт набор даже при той же дате.

Альтернативы: расширить текущие сиды и молча перезаписывать их при старте отвергнуто из-за риска для пользовательских данных. Полный `TRUNCATE` отвергнут по той же причине.

### 2. Декларативные определения и последовательная загрузка

Файлы и их ответственность:

| Файл | Содержимое |
|---|---|
| `app/demo_data/catalog.py` | Два объекта `DEMO-MS-01/02`, поставщики, девять SKU и закупочные условия |
| `app/demo_data/movements.py` | Поступления и расходы с датами-смещениями и постоянными номерами документов |
| `app/demo_data/orders.py` | Будущие ожидаемые заказы; `pending_qty = expected_qty`, `received_qty = 0` |
| `app/demo_data/loader.py` | Одна транзакция загрузки, определение даты существующего набора, итоговые количества |
| `app/demo_data/replacement.py` | Проверка чужих ссылок и точечная очистка демографа |
| `app/demo_data/__main__.py` | `argparse`, проверка `as_of`, код выхода и краткая сводка без строки подключения |
| `app/demo_data/scenarios.py` | Запросы и литеральные эталоны контрольных ответов |

Загрузчик создаёт справочники и условия, затем в хронологическом порядке проводит движения через `app.inventory.operations.register_receipt/register_consume`, после чего создаёт `PurchaseOrder` напрямую. Даты в определениях — целые смещения от `as_of`; даты ожидаемых заказов положительные. Все шаги используют одну сессию и один `commit` в конце; ошибка вызывает `rollback`. `app/seeds/` и Compose при этом не меняются.

Точный состав девяти SKU, смещения дат, количества и особые условия приведены в [fixture-plan.md](fixture-plan.md). Каждой ситуации соответствует отдельный SKU, поэтому API и эталоны можно проверять с фильтром. Ежедневные расходы масла генерируются из компактной декларации.

### 3. Безопасная пересборка по графу связей

Перед удалением загрузчик разрешает демо-ID только по точному перечню ключей из `catalog.py`, `movements.py` и `orders.py`, а не по одному префиксу. Проверить ссылки извне: чужие движения, партии, заказы и условия на демотовар, объект или поставщика; чужие движения и распределения на демопартию; дочерние движения и строки исправлений на демодвижение. Любая такая связь останавливает пересборку до первого удаления. Загрузчик не создаёт исправлений, поэтому обнаруженные `AmendmentEntry` также считаются внешней ссылкой. При отсутствии связей удалить собственные версии, распределения, движения, партии, заказы, блокировки остатков, условия и справочники в порядке ограничений FK. Удаление и новая загрузка находятся в одной транзакции.

Альтернатива — отменять демодвижения через бизнес-сервис и создавать новые — отвергнута: аудит станет неограниченно расти, а активные номера и внутренние ID перестанут давать конечное контрольное состояние.

### 4. Матрица сценариев и независимые эталоны

Определить стабильные сценарии:

| ID | Цель | Контроль |
|---|---|---|
| `oil-quarter-plan` | Целевой вопрос о масле | Расход, остаток, закупка, цена, стоимость, дата и бюджет |
| `lead-time-stockout` | Запас закончится до поставки | `stockout`, дата исчерпания и дни дефицита |
| `expiry-and-writeoff` | Годного запаса больше расхода до срока | `expiring_soon`, `writeoff_risk` и ожидаемое количество |
| `expired-stock` | Просрочка остаётся в учётном остатке | `expired`, учётный и доступный остатки |
| `no-movement` | Нет движения дольше порога | `no_movement` и нулевая закупка |
| `short-history` | История короче 90 дней | `incomplete_history`, знаменатель 90 и число дней истории |
| `unknown-price` | Есть потребность, нет цены | Количество есть, цена/стоимость `null`, бюджет неполон |
| `unknown-lead-time` | Есть потребность, нет условий | Недатированная оценка и причина неполноты |
| `incoming-order` | Заказ уже в пути | Поставка в исходных данных и нет дубля закупки |

Каталог в `app/demo_data/scenarios.py` хранит метод, путь, параметры/тело и ожидания. Для проверки массивов выбирать запись по деловым полям `sku`, `location`, `type` или `doc_number`, а не по индексу; `batch_id` и другие внутренние ID не фиксировать. Передавать `as_of` в каждом запросе; для списков указать `limit=100` либо фильтр, чтобы пагинация не скрыла сценарий. Контрольная дата теста — `2026-09-29`; ожидаемые для `DEMO-OIL` значения `current_stock = 50.000` и `average_daily_consumption = 1.000000` задать литералами. Остальные эталоны количества, дат, типов риска и бюджета вычислить вручную из определений набора и зафиксировать литералами; не получать их вызовом production-функций при выполнении теста.

`tests/test_demo_data_api.py` использует существующий `db_session` из `tests/conftest.py` и `TestClient(app)` по образцу `tests/test_api_procurement_plan_e2e.py`. После загрузки пустой тестовой БД вызвать четыре API и сверить каталог. Отдельные `tests/test_demo_data_loader.py` и `tests/test_demo_data_replacement.py` проверяют состав, идемпотентность, замену, защиту чужих данных и rollback; существующий `tests/test_seeds.py` покрывает неизменность начальных сидов.

### 5. Детерминизм без стабилизации внутренних ID

Проверки сравнивают деловые ключи, даты, Decimal-значения, типы рисков и бюджетные итоги. Поля с суррогатными ID, `created_at` и порядок равных по бизнес-ключам строк нормализуются или не сравниваются. Пересборка может дать другие ID, но тот же предметный результат.

## Risks / Trade-offs

- Демообъём с 90 дневными движениями заметно больше минимальных сидов → генерировать только нужную историю, измерить подготовку в интеграционном тесте.
- Прямое удаление демографа обходит бизнес-аудит → разрешать его только явным `--replace`, в префиксной области и после проверки внешних ссылок.
- Каталог эталонов станет неактуальным при осознанном изменении формул → менять набор и эталоны в одном ревью, не перегенерировывать ожидания из фактического ответа.
- Префикс `DEMO-` технически доступен пользователю → считать любую внешнюю ссылку на демограф блокирующим конфликтом, а не удалять её.

## Migration Plan

Миграция БД не нужна. На изолированном стенде оператор явно запускает CLI с датой стенда. Порядок команд, ограничения `--replace` и маршрут показа записать в `doc/demo-data.md` после фиксации каталога; `README.md` относится к этапу 13. Откат кода не меняет существующую БД; для восстановления демонстрационного стенда использовать его резервную копию или пересоздать изолированную БД.
