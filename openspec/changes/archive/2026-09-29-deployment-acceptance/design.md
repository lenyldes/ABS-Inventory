# Technical Design: Развёртывание и приёмочные испытания стенда

## Context

См. [proposal.md](proposal.md) для описания целей. Приложение состоит из трёх основных сервисов:
- `db`: PostgreSQL 18.4
- `app`: FastAPI бэкенд (Python 3.11)
- `web`: Nginx (Alpine), отдающий статику фронтенда и проксирующий API/документацию на `app:8000`.

На сервере `pi5server` (`pi_server_from_internet`) в каталоге `~/caddy-proxy` функционирует Caddy 2, подключённый к внешней Docker-сети `caddy-public`. Домен `abs-inventory.lenyldes.ru` направлен на публичный IP сервера.

## Goals / Non-Goals

**Goals:**
- Обеспечить надёжное и воспроизводимое развёртывание стека на целевом сервере без нарушения локального тестового окружения.
- Настроить маршрутизацию HTTPS-запросов через Caddy с автоматическим TLS-сертификатом.
- Провести приёмочные испытания (Acceptance testing) работоспособности API, UI, демоданных и логирования.
- Актуализировать статус проекта в `doc/ROADMAP.md` (пропуск этапа 11 и закрытие этапа 12).

**Non-Goals:**
- Интеграция внешней LLM и чата AI-помощника (этап 11 пропущен по указанию пользователя).
- Изменение структуры бизнес-логики и контрактов API.

## Decisions

### 1. Использование дополнительного файла `docker-compose.prod.yml`
- **Решение**: Добавить `docker-compose.prod.yml`, определяющий включение сервиса `web` (с фиксированным именем контейнера `abs_web`) во внешнюю сеть `caddy-public`:
  ```yaml
  services:
    web:
      container_name: abs_web
      networks:
        - default
        - caddy-public

  networks:
    caddy-public:
      external: true
  ```
- **Обоснование**: Базовый `docker-compose.yml` остаётся полностью независимым от внешних сетей, поэтому локальный запуск тестов `bash scripts/check.sh` на машинах разработчиков не требует наличия сети `caddy-public`.
- **Альтернативы**: Включение сети `caddy-public` непосредственно в `docker-compose.yml` (приводит к ошибкам локального запуска при отсутствии сети).

### 2. Точка входа в стек через `abs_web`
- **Решение**: Caddy перенаправляет запросы к домену `abs-inventory.lenyldes.ru` на `abs_web:80`. Контейнер `abs_web` (Nginx) отдаёт фронтенд и проксирует запросы к `/api/`, `/health`, `/docs` и `/openapi.json` во внутреннюю сеть на `abs_app:8000`.
- **Обоснование**: Единая точка входа исключает необходимость публикации внутренних портов бэкенда и БД наружу, обеспечивая изоляцию сервисов.
- **Альтернативы**: Раздельная маршрутизация Caddy на фронтенд и бэкенд (дублирует логику `nginx.conf`).

### 3. Автоматический TLS и редирект в Caddy
- **Решение**: В `~/caddy-proxy/Caddyfile` активировать блок:
  ```caddy
  abs-inventory.lenyldes.ru {
      reverse_proxy abs_web:80
  }
  ```
- **Обоснование**: Caddy автоматически запрашивает сертификат у Let's Encrypt / ZeroSSL по ACME HTTP-01/TLS-ALPN-01 и настраивает постоянный редирект с HTTP (порт 80) на HTTPS (порт 443).

### 4. Протокол приёмочных испытаний
- **Решение**: Выполнить серию валидационных проверок:
  1. Сетевая проверка: резолв домена, валидность TLS-сертификата, HTTP-308/301 редирект на HTTPS.
  2. Проверка здоровья и контрактов: `/health`, `/docs`, `/api/warehouse/inventory`, `/api/forecast`, `/api/alerts`, `/api/procurement/plan`, `/api/budget`.
  3. Проверка функциональности UI: загрузка всех экранов, выполнение тестовой складской проводки.
  4. Проверка сброса демоданных: вызов операции пересборки данных и подтверждение возврата к эталону.
  5. Проверка логирования: инспекция логов `docker compose logs`.

## Risks / Trade-offs

- **[Специфика ARM64 на Raspberry Pi 5]** → Базовые образы `python:3.11-slim`, `postgres:18.4` и `nginx:alpine` проверены на arm64; сборка и запуск происходят штатно.
- **[Ограничения ресурсов сервера]** → Приложение потребляет менее 500 МБ RAM суммарно; фоновые процессы других проектов не затрагиваются.
- **[Задержка выпуска сертификата Caddy]** → Домен уже указывает на IP сервера; ACME-челлендж проходит за секунды.
