# Запуск и проверка основы приложения

## Конфигурация

Скопируйте `.env.example` в `.env`. Файл `.env` предназначен для локальных значений и не включается в репозиторий.

- `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` задают пользователя, пароль и рабочую БД PostgreSQL. Те же значения должны быть указаны в `DATABASE_URL`.
- `POSTGRES_PORT` публикует порт PostgreSQL на хосте; `PORT` публикует HTTP-порт приложения. Внутри Compose приложение подключается к хосту `db:5432`.
- `TEST_DATABASE_URL` строго обязателен для запуска тестов и должен указывать на отдельную тестовую БД (например, `abs_inventory_test`). Запуск тестов на рабочей БД `abs_inventory` или системной `postgres` блокируется защитным отказом.
- `APP_ENV` задаёт окружение приложения; для тестов строго требуется `APP_ENV=test`.
- `ABS_*_CONTAINER` (`ABS_DB_CONTAINER`, `ABS_APP_CONTAINER`, `ABS_TEST_CONTAINER`) позволяют переопределить имена контейнеров при запуске изолированного Compose-проекта (например, через флаг `-p` с отдельными портами).

Параметры `POSTGRES_*` инициализируют только пустой том. Их изменение после первого запуска само по себе не меняет существующего пользователя или БД.

## Запуск

Из корня проекта выполните `docker compose up --build`. Compose дождётся готовности PostgreSQL. Приложение последовательно применит миграцию, загрузит идемпотентные сиды и запустит HTTP. Если миграция или загрузка завершится ошибкой, сервер не запустится; причина будет в журнале контейнера.

Откройте `http://localhost:8000/health`, если `PORT` оставлен по умолчанию. Эндпоинт возвращает:
- `200 healthy` — база доступна, ревизия Alembic актуальна и все 12 предметных таблиц присутствуют;
- `503 unhealthy` — база недоступна либо схема повреждена/не готова (несовпадение ревизий, отсутствие таблиц).
Ответ никогда не содержит учетных данных и параметров подключения.

Обычная остановка `docker compose down` сохраняет именованный том. При следующем `docker compose up` миграция и сиды выполнятся повторно, не создавая дубликатов и не перезаписывая пользовательские данные. Команда `docker compose down -v` удаляет том и его данные.

## Отдельные команды в контейнере

После запуска PostgreSQL можно выполнить:

```bash
docker compose run --rm app alembic upgrade head
docker compose run --rm app python -m app.seeds
docker compose run --rm test ruff check .
docker compose run --rm test ruff format --check .
docker compose run --rm test pytest -q
bash scripts/test_compose_lifecycle.sh  # сквозной тест Compose на отдельном томе
bash scripts/test_compose_failure.sh    # тест сбоя миграции и сидов во время запуска Compose
```

Сервис `test` передает `APP_ENV=test`, изолированный `TEST_DATABASE_URL` и рабочий `MAIN_DATABASE_URL`. В коде действует двухуровневый защитный отказ:
1. Сессионная фикстура проверяет `APP_ENV == 'test'`, наличие `TEST_DATABASE_URL` и его отличие от рабочей БД (включая исходный `DATABASE_URL` с нестандартным именем) до подмены переменных и применения миграций.
2. Фикстура сессий БД блокирует выполнение `TRUNCATE`, если целевая база не является тестовой (обязательно наличие `'test'` в имени БД и несовпадение с рабочими URL).

Локальное виртуальное окружение и установка зависимостей в системный Python не нужны.

На этапе 05 сиды содержат только товары, объекты, поставщиков и закупочные условия. Партии, движения и складской API появятся на этапе 06.
