# Design

## Context

Первая версия сайта, её запуск и демонабор описаны в `initial-design.md`. Сейчас `web/index.html` показывает подробные разделы склада, журнала и аналитики, а `web/js/api.js` скрывает исходный HTTP-статус и тело ошибки от вызывающего кода. Новый маршрут проверки строится на существующих API и общем томе БД. Точные контрольные примеры вынесены в `verification-cases.md`.

## Goals / Non-Goals

**Goals:** дать человеку без технической подготовки готовые действия с реальными запросами, ответами и понятными выводами; сохранить подробные экраны и малый размер модулей.

**Non-Goals:** новые API и миграции, отдельная БД или сеанс на посетителя, чат, публикация стенда и клиентский `README.md`.

## Decisions

### Проверка задания


Новый первый экран в `web/index.html` ведёт по карточкам обязательных возможностей; подробные разделы доступны на втором экране. `web/js/main.js` после `/api/demo/status` передаёт `state.asOf` в `initVerification()`; отдельная проверка не запускает запросы автоматически. `web/js/verification-read.js` и `web/js/verification-write.js` хранят небольшие группы построителей запросов и извлечения ключевых полей по `verification-cases.md`. `web/js/verification.js` управляет кнопками, последовательными шагами, состояниями и DOM. `web/js/api.js` получает общий низкоуровневый обмен, который возвращает фактические метод, URL, тело запроса, HTTP-статус и JSON ответа как для 2xx, так и для ошибок; прежние `getJson`, `postJson`, `getAllPages` сохраняют сигнатуры и поведение. Карточка выводит только обмены своего нажатия, не фоновый трафик склада.

После ревью экраны разделены через `web/js/screens.js`: по умолчанию видна проверка эндпоинтов, ссылки ведут к отдельному подробному маршруту с заглушкой AI в конце. `web/js/verification-request.js` заранее рисует редактируемые поля подготовленного запроса. `verification.js` показывает действие и запрос до запуска, блокирует поля на время обмена и добавляет ответ с результатом после него. Для повторной записи пользователь сначала подготавливает новый документ, видит его номер, затем запускает проверку. Зависимые запросы к партиям видны заранее, повтор документа явно описан как точная копия первого успешного запроса.

После второго ревью две ссылки вынесены в крупные блоки сразу под уменьшенной шапкой. Карточка сделана нативным `details`: `summary` содержит название проверки, маршрут и статус. Раскрытый запрос занимает всю ширину карточки; ответ и результат добавляются под ним. Отдельная колонка «Действие» удалена: назначение шага указано у запроса.

Для постоянного стенда после согласования добавлен сброс при каждом запуске `app`: после миграций `app.demo_data.reset` выполняет `TRUNCATE ... RESTART IDENTITY CASCADE` для всех предметных таблиц в одной транзакции, не затрагивая `alembic_version`; затем идут сиды и bootstrap. Это удаляет движения посетителей, в том числе для `DEMO-`, и обновляет дату набора. Форма и проверочные карточки больше не блокируют `DEMO-`. Читающий статус требует обязательные ключи, но допускает дополнительные движения и партии посетителей. Поля с закрытым набором (`type` движения и предупреждения) показываются списком; даты и числа получают соответствующие типы ввода.

Контракт нового клиента: `exchangeJson(method, path, {params, body, signal})` возвращает `{request: {method, url, body}, response: {status, body}, error}`; для HTTP 4xx `error=null` и сохраняется JSON, для сетевого сбоя `status=null`, для ошибки разбора сохраняется HTTP-статус и `error.kind="invalid_json"`. `request.url` — относительный путь с сериализованными query-параметрами, `body=null` для GET. Адаптеры `getJson`/`postJson` поверх этого обмена сохраняют существующий `ApiError`. В `verification.js` каждый запуск создаёт собственный список обменов и передаёт его рендеру карточки; начальное состояние не содержит фиктивного ответа. `verification-read.js` получает `asOf` и возвращает набор готовых шагов; `verification-write.js` получает дату Москвы и идентификатор запуска, ведёт зависимые шаги и отдаёт данные для вывода, не обращаясь к DOM.

Для записи JS генерирует короткий случайный идентификатор и документы `CHECK-*` для предзаполненных `OIL-001`/`MS-01`; SKU можно изменить, включая `DEMO-`. Каждый успешный шаг записи обновляет существующие склад и журнал через точку подключения `warehouse.refreshAfterMovement()`. Связанные шаги (`receipt` → `consume`, первый документ → `409`) выполняются по очереди; при сбое первого второй не отправляется. Результат FEFO строится по реальным `allocations` и запросу детализации выбранного SKU, без обещания фиксированной партии после повторов. `scripts/test_web_ui_e2e.sh` проверяет HTTP-обмен через прокси, а `doc/ui-demo.md` описывает нажатия и ожидаемые признаки.

Альтернатива — отдельный backend сеансов или копия БД на посетителя — отклонена после согласования общего набора: это меняло бы API и эксплуатацию. Альтернатива — показывать заранее заготовленный JSON — не доказывает работу сервера. Новых API-маршрутов, миграций и зависимостей нет. Точные входы и выходы чистого стенда: `verification-cases.md`.

## Risks / Trade-offs

- Общая БД накапливает документы → номера уникальны, числовые остатки записывающих шагов берутся из ответа; точные эталоны применяются только в изолированном Compose-тесте.
- Посетители могут менять `DEMO-` через сайт или API → карточки показывают фактический ответ, а следующий запуск приложения восстанавливает исходные данные.
- Клиент может не получить ответ после успешной записи → повтор создаёт новый документ и явно показывает фактический результат; автоматического скрытого повтора POST нет.

## Migration Plan

Миграция схемы не нужна. После `alembic upgrade head` команда Compose транзакционно очищает предметные таблицы через `app.demo_data.reset`, сохраняя `alembic_version`, затем выполняет сиды и bootstrap демонабора. Любой запуск app удаляет движения посетителей и восстанавливает контрольную дату на текущий день Москвы. Откат этой политики требует вернуть прежнюю команду запуска Compose; уже удалённые записи не восстановятся.
