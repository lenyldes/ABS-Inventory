# Контрольные действия сайта

Этот документ дополняет `design.md`. `as_of` берётся только из `GET /api/demo/status`; дата `2026-09-29` ниже — фиксация для изолированного теста. В рабочем стенде календарные даты рассчитываются от полученного `as_of`, а не зашиваются в JS. `today` для записей — текущая дата Москвы. Все HTTP-обмены идут через адрес сайта.

Значения ниже предзаполняют редактируемые поля карточек. Если проверяющий меняет их до запуска, карточка отправляет изменённый запрос и показывает расхождение с контрольным примером там, где эталон зависит от исходных значений.

## Читающие действия на DEMO-

| Карточка и фактический запрос | Результат, выделяемый из ответа 200 |
|---|---|
| Остаток: `GET /api/stock?sku=DEMO-OIL&location=DEMO-MS-01&as_of=2026-09-29&limit=50&offset=0` | Одна строка `DEMO-OIL`/`DEMO-MS-01`: `current_stock=50.000`, `available_stock=50.000`, `average_daily_consumption=1.000000`, `days_of_stock=50.0`, `nearest_expiry_date=2027-03-28`. Полный объект ответа с `total`, `limit`, `offset` раскрывается. |
| Партии и просрочка: `GET /api/stock/DEMO-EXPIRED?location=DEMO-MS-01&as_of=2026-09-29` | В выбранном объекте `current_stock=10.000`, `available_stock=0.000`, `expired_stock=10.000`; партия с количеством, сроком, ценой и `receipt_doc_number` показана из `locations[].batches[]`. |
| Журнал: `GET /api/movements?sku=DEMO-OIL&location=DEMO-MS-01&date_to=2026-09-29&limit=2&offset=0` | `items.length=2`, `total>2`, `limit=2`, `offset=0`; отдельная кнопка «Следующая страница» отправляет тот же запрос с `offset=2` и показывает новые строки и распределения из `allocations`. |
| Прогноз: `POST /api/forecast` с `{"sku":"DEMO-OIL","location":"DEMO-MS-01","as_of":"2026-09-29","horizon_months":3}` | `current_stock=50.000`, `average_daily_consumption=1.000000`, `recommended_qty=45.000`, `total_cost=4500.00`, `order_date=2026-11-11`; показываются `incoming_qty`, `safety_stock`, `reorder_point`, `explanation` и предупреждения из того же ответа. |
| Риск дефицита: `GET /api/alerts?sku=DEMO-DEFICIT&location=DEMO-MS-02&type=stockout&as_of=2026-09-29&limit=50&offset=0` | Предупреждение `stockout` уровня `critical`: `available_stock=5.000`, `lead_time_days=10`, `days_of_stock=5.0`; уровень и исходные метрики показаны вместе. |
| Нет движения: `GET /api/alerts?sku=DEMO-IDLE&location=DEMO-MS-01&type=no_movement&as_of=2026-09-29&limit=50&offset=0` | Предупреждение `no_movement` уровня `info`, `no_movement_days_threshold=90`. |

Ключевые значения выше проверяются на чистом тестовом наборе. В браузере выводятся значения полученного JSON; если целевая строка исчезла или статус не тот, карточка показывает расхождение и полный ответ, а не эталон как будто это ответ сервера.

## Действия с записью на общем OIL-001 / MS-01

Каждая операция создаёт новый `doc_number` длиной до 64 символов; пример `CHECK-R-<случайный-идентификатор>`. Повторное нажатие создаёт другой номер. Числовой остаток берётся из ответа и меняется после других проверок. Номер и фактические ID показываются в цепочке.

| Карточка и запрос | Проверяемый результат |
|---|---|
| Приход: `POST /api/movements` с `operation_date=today`, `sku=OIL-001`, `location=MS-01`, `type=receipt`, `quantity="2.000"`, новым `doc_number`, `batch_number=CHECK-B-<тот же идентификатор>`, `expiry_date=today+1`, `unit_price="100.00"` | `201`, положительный `id`, `type=receipt`, тот же документ, `current_stock` и `available_stock`; затем `GET /api/stock/OIL-001?location=MS-01&as_of=today` подтверждает новую партию и остаток. Каждая отправка и ответ показаны отдельно. |
| Расход FEFO: после прихода из предыдущего шага `POST /api/movements` с `operation_date=today`, `sku=OIL-001`, `location=MS-01`, `type=consume`, `quantity="1.000"`, новым `doc_number` | `201`; сумма `allocations[].quantity` равна `1.000`; карточка связывает `batch_id` ответа с партией из запроса детализации и показывает её срок. Сайт объясняет фактически выбранную партию и новый остаток; он не утверждает, что расход всегда пойдёт именно из только что созданной партии. |
| Неизвестный SKU: `POST /api/movements` с данными `consume`, `sku=CHECK-UNKNOWN-SKU`, `quantity="1.000"`, новым номером | `404`, русское `message` и машинный `code`; успешного движения нет. |
| Неизвестный объект: `POST /api/movements` с данными `consume`, `sku=OIL-001`, `location=CHECK-UNKNOWN-LOCATION`, `quantity="1.000"`, новым номером | `404`, русское `message` и машинный `code`; успешного движения нет. |
| Нулевое количество: `POST /api/movements` с данными `consume`, `quantity="0"`, новым номером | `422`, `code=VALIDATION_ERROR`, сообщение об обязательном положительном количестве. |
| Нулевой приход: `POST /api/movements` с данными `receipt`, `quantity="0"`, новым номером и обязательными `batch_number`, `unit_price` | `422`, `code=VALIDATION_ERROR`, сообщение об обязательном положительном количестве. |
| Избыточный расход: `POST /api/movements` с данными `consume`, `quantity="1000000.000"`, новым номером | `422`, `code=INSUFFICIENT_STOCK`, в `details.available` указано доступное количество; карточка показывает его из фактического ответа. |
| Будущая дата: `POST /api/movements` с данными `consume`, `operation_date=today+1`, `quantity="1.000"`, новым номером | `422`, ошибка будущей даты. |
| Повтор документа: сначала успешный `consume` на `1.000` с новым номером, затем тот же JSON второй раз | Первый ответ `201`, второй `409`; оба обмена показаны, в результате второго нет нового ID операции. Если первый запрос не удался, второй не отправляется. |

На чистой БД у `OIL-001`/`MS-01` сидовый остаток `16.000`. Контрольный приход `2.000` даёт `18.000`, следующий расход `1.000` даёт `17.000`. Эти числа применимы только к изолированному тесту без других операций. На общем стенде карточки показывают текущие данные и не сравнивают их с `18.000`/`17.000`.

## Состояния интерфейса

- После нажатия текущая карточка показывает загрузку; другая фоновая загрузка не подменяет её обмен. Повторное нажатие во время запроса заблокировано.
- Для каждого шага показываются метод, относительный URL с query, отправленное тело либо «без тела», статус и тело ответа. Полный JSON раскрывается через доступный с клавиатуры элемент `details`; основные числа видны без раскрытия.
- При сетевой ошибке статус обозначается «ответ не получен», тело отсутствует; при невалидном JSON показывается фактический статус и ошибка разбора. Ожидаемый `404`/`409`/`422` подписывается как успешная проверка отказа, но никогда как успешно проведённая операция.
- Перезагрузка страницы не очищает общую БД; новая запись использует новый номер. Через редактируемые поля запроса можно провести движение для любого существующего SKU, включая `DEMO-`. Запуск приложения заново восстанавливает исходный набор; подробные экраны доступны на втором экране сайта.
