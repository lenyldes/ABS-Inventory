# Проверки первой версии сайта

## Контрольные примеры

| Условие / запрос | Ожидаемый результат |
|---|---|
| Чистая БД, Москва `2026-09-29`, `docker compose up` | `GET /api/demo/status` → 200, `ready=true`, `as_of=2026-09-29`; после перезапуска дата та же, набор не удвоен |
| `GET /api/stock?as_of=2026-09-29&limit=100`, пара `DEMO-OIL`/`DEMO-MS-01` | `current_stock=50.000`, `available_stock=50.000`, `average_daily_consumption=1.000000`, `days_of_stock=50.000` |
| `GET /api/stock/DEMO-EXPIRED?as_of=2026-09-29` | Учётный остаток 10.000, доступный 0.000 |
| `POST /api/procurement/plan` с `{"as_of":"2026-09-29","horizon_months":3}` на контрольном наборе | Позиция `DEMO-OIL`/`DEMO-MS-01`: дата заказа `2026-11-11`, 30.000, 3000.00 руб.; известная часть бюджета 20300.00 руб. |
| Форма `receipt` для `OIL-001`/`MS-01`, `quantity=2.000`, новый `doc_number`, партия и цена | 201; новый остаток и документ видны в форме, складе и журнале |
| Форма с `sku=DEMO-OIL` | HTTP-запрос не выполняется, видна причина запрета |

Последний бюджетный эталон сверяется на наборе без посторонних платных закупок; на постоянно работающем стенде результаты могут измениться из-за действий через публичный API. Все точные числа уже зафиксированы в `app.demo_data.scenarios` и проверяются существующим `tests/test_demo_data_api.py`.

## Risks / Trade-offs

- Публичный `POST /api/movements` позволяет обойти ограничение формы и изменить общий снимок → UI защищает контрольный маршрут от случайной правки; ограничения публичного API и восстановление стенда рассматриваются на этапе 12.
- Дата набора остаётся прежней после перезапуска через дни → сайт явно показывает `as_of` и использует её во всех аналитических запросах.
- Nginx может отдать HTML раньше готовности API при сбое запуска → UI показывает ошибку; `web` ожидает здоровый `app` при штатном старте.
- Новые пути Compose могут сломать существующие сквозные проверки → обновить ожидания и проверить на изолированных проектах через единый `scripts/check.sh`.

## Migration Plan

Миграция схемы БД не нужна. На чистом томе демонабор создаётся автоматически; на существующем томе без `DEMO-` он добавляется при первом старте новой версии, остальные записи сохраняются. Для отката возвращаются прежние команда `app` и Compose-конфигурация; созданный демонабор остаётся в БД и может быть удалён только штатной явной процедурой управления данными.
