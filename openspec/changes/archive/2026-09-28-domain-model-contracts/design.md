# Предметная модель и архитектурные границы

## Context

Мотивация и объём — в [proposal.md](proposal.md). Приложения, БД и тестов пока нет. Источники — [ROADMAP и ссылки на ТЗ/БТ](../../../doc/ROADMAP.md). Ниже сохранены решения этапа 04; названия сущностей обозначают модель, а не готовые ORM-классы.

## Goals / Non-Goals

**Цели:** связать правила шести спецификаций с моделью данных, обеспечить атомарность учёта и исправлений, отделить расчёты от транспорта и хранения, сохранить контекст между сессиями.

**Вне целей:** создание Python-кода, SQL-схем, миграций и Docker; реализация этапов 05–07; воспроизведение старых ответов по состоянию знаний до исправлений. Архивация этого изменения утверждает модель, но не означает работающий API.

## Decisions

### 1. Модульный монолит и независимые расчёты

Одно приложение FastAPI и одна PostgreSQL. Внутри — справочники, склад, прогнозирование, закупки. API валидирует вход; сервисы управляют сценариями и транзакциями; доступ к данным изолирован. Детерминированные формулы и дневной прогноз получают подготовленные данные и проверяются без HTTP и БД. Обязательный стек: Python 3.11, SQLAlchemy, Pydantic, Alembic, pytest и Docker Compose.

Несколько сервисов усложняют общие транзакции; расчёты внутри API затрудняют тестирование и повторное использование.

### 2. Сущности и связи

| Сущность | Данные и связи |
|---|---|
| Товар | Уникальный SKU, название, категория, базовая единица; основной поставщик расчёта |
| Объект | Уникальный код, название; один логический склад |
| Поставщик | Уникальный идентификатор и название; начальные записи в сидах, базовый API создания и чтения; множество закупочных условий и поступлений |
| Закупочные условия | Товар + поставщик; срок в календарных днях, упаковка, минимум, ориентировочная цена |
| Партия | Товар + объект, маркировка, дата поступления, годность, цена; ссылка на приход |
| Движение | Идентификатор, дата операции, время регистрации, товар, объект, тип, количество, документ; причина по смыслу операции |
| Распределение движения | Идентификатор строки, ссылка на движение и партию, количество; у расхода несколько строк |
| Возврат | Движение со ссылками на исходный расход и конкретную строку его распределения; исходная партия и цена сохраняются |
| Ожидаемая поставка | Товар, объект, поставщик, ожидаемая дата и количество; связи с частичными поступлениями |
| Набор исправлений | Причина, затронутые операции, исходные версии, предлагаемые изменения, результат просмотра и подтверждения |
| История версий | Исходное и исправленное содержание, время изменения, причина; отмена сохраняет запись |

Документ пока не выделяется в многотоварный агрегат: номер относится к одному движению и уникален на объекте среди активных записей (при отмене номер освобождается, аудит сохраняется). Строки накладной получают номера с суффиксами. Новое поступление создаёт новую учётную партию даже при одинаковой маркировке производителя. Отдельно изменяемый остаток не хранится.

Точные SQL-типы, ограничения и индексы выбираются при подготовке БД в рамках этих правил. Количество — точное десятичное до 0,001, штуки целые; денежные значения — рубли до копеек. Двоичные дроби для расчётов исключены.

### 3. Фактическая история и ошибки ввода

Обычный расход автоматически распределяется по FEFO. Порядок FEFO детерминирован: срок годности (бессрочные в конце), дата поступления, время регистрации партии `created_at`, `batch_id`. Внутри одной даты операции учитываются в бизнес-порядке: приход/возврат -> расход/списание -> инвентаризация; внутри типа — по времени регистрации. Распределение считается записью фактической выдачи, поэтому позднее поступление его не переписывает. При исправлении фактической партии разрешено явное отступление от FEFO с причиной; годность и обеспеченность проверяются на дату расхода.

Инвентаризация (`correction`) отражает расхождение факта и учёта; неверный ввод исправляется версией исходной операции. Политика «только текущая корректировка» отвергнута: она теряет действительную дату и смысл забытого прихода. Автоматическое перераспределение всей истории отвергнуто: оно может приписать выдаче партию, которую фактически не использовали.

Прошлые даты разрешены с проверкой остатков на каждый день и движение от даты операции до текущего дня. Набор связанных исправлений проверяется целиком. Механизм правок разрешает менять количество, дату, номер документа, партию конкретной строки расхода по её `allocation_id`; объект прихода — только при отсутствии расходов на старом объекте; смена SKU запрещена (только отмена и новое движение). Отмена убирает влияние движения, освобождает номер документа и сохраняет аудит.

### 4. Транзакции и согласованность

Изменения сериализуются по паре «товар + объект» внутри транзакции PostgreSQL. Защита охватывает и пустой остаток, а не только существующие строки партий. При нескольких парах блокировки берутся в стабильном порядке. Проверка и запись выполняются под одной защитой; ошибка откатывает весь набор.

Способ блокировки выбирается при детализации БД с сохранением инварианта. Одной проверки количества до транзакции недостаточно.

Предварительный просмотр исправления ничего не проводит. Подтверждение сверяет исходные версии и значимое состояние зависимостей; устаревший просмотр возвращает `409`. Контроль должен замечать и новую зависимую операцию, а не только смену версии редактируемой записи. Связь приёмки с ожидаемой поставкой обновляется атомарно с движением.

Прогноз читает остатки, движения, цены и поставки из одного согласованного снимка БД. Длинная транзакция предварительного просмотра не удерживается до пользовательского подтверждения.

### 5. Временная модель и расчётные правила

`as_of` определяет дату актуальности, по умолчанию текущий день в часовом поясе `Europe/Moscow`. Время суток отсекается, расчёт ведётся в календарных сутках. Прибавка месяцев сдвигает дату с фиксацией на последний день месяца при нехватке дней (31 января + 1 месяц = 28/29 февраля). Используется актуальная исправленная история на дату `as_of`. Окно потребления — 90 дней включительно по `as_of`; прогноз начинается с `as_of + 1`. Неполная история сохраняет знаменатель 90 и возвращает флаг `is_history_complete: false` с предупреждением.

Дневной прогноз моделирует строгую хронологию каждого дня: 1) исключение утренней просрочки (`expiry_date < t`) в риск списания; 2) приход ожидаемой поставки дня (непринятые поставки с датой $\le as\_of$ считаются задержанными и исключаются из будущего покрытия); 3) списание дневного расхода $a$ по FEFO с фиксацией суточного дефицита (остаток не падает ниже 0); 4) фиксация остатка на конец дня. Будущие поставки и заказ предполагаются годными на весь горизонт. Если возникает временный разрыв до прихода поставки, система фиксирует интервал дефицита, а итоговый заказ закрывает суммарную нехватку и страховой запас к концу периода.

Расчёты используют `Decimal`: не менее 6 знаков для промежуточного среднего расхода, 3 знака для количеств, 2 знака для цен и стоимости (`ROUND_HALF_UP`). При $S=0$ порог заказа — падение остатка до нуля (если запас не исчерпывается, заказ равен 0, а даты `null`). Недоступные из-за нехватки данных или деления на ноль величины ($a=0$, нет срока, нет цены) строго возвращают `null` с кодами в `warnings`, без фиктивных нулей.


### 6. Основа API и ошибок

Состав обязательных запросов и ответов определён в спецификациях [склада](specs/inventory/spec.md), [прогноза](specs/forecasting/spec.md) и [предупреждений](specs/alerts/spec.md). [Исправления](specs/movement-amendments/spec.md) добавляют просмотр и подтверждение набора правок с проверкой зависимостей.

Ошибки имеют машинный код, русское сообщение и детали. `400` — некорректное сочетание параметров; `404` — неизвестная сущность; `409` — документ-дубликат или конфликт актуальности; `422` — недопустимое значение, будущая дата, нехватка количества либо нарушение учёта. Полные JSON-схемы и маршруты расширения уточняются задачами контрактов.

### 7. Контекст следующей сессии

До архивации источником служит это изменение; после синхронизации — `openspec/specs/`. Дизайн сохраняется вместе с изменением в архиве. AGENTS.md требует читать ROADMAP, активные изменения, релевантные спецификации и связанный дизайн, а не полагаться на переписку. При архивации ссылка ROADMAP на дизайн обновляется на фактический архивный путь. Текущие спецификации имеют приоритет перед устаревшими решениями старых архивов; противоречия требуют обсуждения.

## Risks / Trade-offs

- Поздний приход выявляет историческое отступление от FEFO → показать его, сохранить фактическое распределение; изменение только явно.
- Неполная история занижает среднее → делить на согласованные 90 дней и предупреждать о качестве исходных данных.
- Структурная проверка OpenSpec не доказывает полноту контрактов → отдельная сверка сценариев и задач перед закрытием этапа.
- Спецификации раньше кода → ROADMAP и tasks явно различают проектирование и реализацию.
- Пограничные правила ещё не обсуждены в деталях → уточнить их задачами этапа 04 до зависимой реализации; не выдавать их за согласованные решения.

## Migration Plan

Миграций БД здесь нет. После ревью и отдельного подтверждения фиксируются артефакты. Затем завершаются задачи детализации этапа 04; по запросу пользователя спецификации синхронизируются, изменение архивируется, ссылка ROADMAP обновляется. Коммит архива и слияние требуют установленного ревью. Откат документационного изменения выполняется средствами Git, данные приложения не затрагиваются.
